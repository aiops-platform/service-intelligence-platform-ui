# v2.2.2 — feat: Problem Center「分析new」改走 agentflow 工作流；修复 agentflow 调用缺租户头导致 agent 无工具

**日期**: 2026-09-17

**需求/背景**: Problem Center 的「分析new」此前直连 HolmesGPT 诊断服务（spike `POST /diagnose/logs`），
诊断逻辑在 spike 侧、与 agentflow 的 agent/MCP 体系并行两套。本次把「分析new」收编到 agentflow：
起一次 `problem-log-diagnose` 工作流 run（triage → logs → know → locate → rca → plan → approve-plan），
run_id 绑回问题单，前端复用既有的 run 查看器轮询进度与提交审批。

**顺带修掉一个静默故障**：本页此前的 agentflow 调用**全都不带 `X-Tenant-ID`**，run 会落到 agentflow 的
dev 缺省租户 `local`，而那里没有任何 MCP server 绑定 → agent 拿不到工具，只能靠提示词空转。

> ⚠️ 本文件是**事后补写**（改动于 2026-09-17 完成但未随代码提交，2026-09-18 补录）。
> 版本号沿用 package.json 当前的 2.2.2（本仓允许同版本多 changelog，见 `v2.2.1-hide-value-pool` 与
> `v2.2.1-hide-ticket-workspace-entries`）。

## 改动明细

### 1. `js/app.js` — 新增 `agentflowFetch()`，统一携带 agentflow 租户头 (line 3699-3724)

**原因**: agentflow 侧租户与 APM 侧租户**故意不同**（问题单在 APM `default`，workflow/MCP/agent 绑定在
agentflow `otr`，两侧由 APM 的 `APM_AGENTFLOW_TENANT` 桥接）。页面原先用裸 `fetch`，
导致 run 落到 agentflow dev 缺省租户 `local`——那里没有 MCP 绑定。

```js
// before：裸 fetch，无租户头
fetch(AGENTFLOW_BASE + '/runs/' + encodeURIComponent(rid))

// after：统一收口，恒带 X-Tenant-ID
var AGENTFLOW_TENANT = localStorage.getItem('agentflowTenantId') || 'otr';
function agentflowFetch(path, options) {
    var headers = { 'X-Tenant-ID': AGENTFLOW_TENANT };
    /* …合并 opts.headers、body 时补 Content-Type… */
    return fetch(AGENTFLOW_BASE + path, { method, headers, body });
}
```

改挂 `agentflowFetch` 的调用点共 5 处：`/workflows`(4118)、`/runs/{id}`(4939)、
`/runs/{id}/traces`(5061)、`/runs/{id}/{approve|reject}`(5413)。

### 2. `js/app.js` — 新增 `resolveLogDiagnoseWorkflowId()` (line 3706, 3726-3747)

**原因**: workflow 的真源是 agentflow 数据库（不是仓库 YAML），前端只能按 **name** 解析 id。
解析结果缓存进 `pcLogWfId`，并发用 `pcLogWfBusy` 挡。找不到时给**可执行**的提示——
这条流程是 seed 出来的，库里没有它「分析new」必然失败：

```js
throw new Error('未找到流程 ' + LOG_DIAGNOSE_WF_NAME +
    '（先在 multi-agent-workflow 跑 scripts/seed_problem_log_diagnose.py --tenant ' + AGENTFLOW_TENANT + '）');
```

### 3. `js/app.js` — `startDiagnose()` 改走 APM `/analyze` (line 4218-4245)

**原因**: 起 run 仍走 APM 而非浏览器直连 agentflow——**绑定与起 run 是原子的一步**。浏览器直连 `/run`
再补绑定，中间失败会留下「起了 run 但没绑定」的孤儿 run：列表上看不见、也打不开。租户桥接也在 APM 内部完成。

```js
// before：直连 spike
apmApi('/v1/problems/' + recordId + '/diagnose', { method: 'POST', body: {} })
  → toast '分析已启动 · <session_id>'

// after：解析 workflow → APM 起 agentflow run
resolveLogDiagnoseWorkflowId()
  .then(wfId => apmApi('/v1/problems/' + recordId + '/analyze',
                       { method: 'POST', body: { workflow_id: wfId, rerun: true } }))
  .then(data => { toast '分析已启动 · ' + data.run_id; openProblemRun(rec, data.run_id); refresh(); })
```

`rerun: true`：引擎没有「重跑同一个 run」的语义，打回后重跑只能起新的一轮。

### 4. `js/app.js` — 表格 Actions 列改绑 `agent_run` (line 3909-3925)

**原因**: 「已发起分析」的绑定真源从 `diagnose_session`（spike）换成 `agent_run`（agentflow）。
同时**删除**了独立的 `View analysis` 按钮——它的落点与 `View diagnosis` 合流为同一个 run 视图。

| | before | after |
|---|---|---|
| 已发起判定 | `findDiagnoseSession(p)` | `findAgentRun(p)` |
| 按钮置灰提示 | `Diagnosis already started` | `Analysis already started` |
| `View analysis` 按钮 | `in_progress` 行显示 | **删除**（合流进 `View diagnosis`） |
| `Ignore` 按钮 | 仅 `pending` 行显示 | `pending` / `in_progress` 均显示 |

### 5. `js/app.js` — `view-diagnosis` 落点改为 run 视图 (line 3966)

```js
// before
else if (act === 'view-diagnosis') openDiagnosisView(rec);
// after
else if (act === 'view-diagnosis') openProblemRun(rec); // 分析new 的产物也是一个 run
```

> ⚠️ **副作用**：`openDiagnosisView()`（诊断结论版面 `#pcDiagnoseOverlay`）自此**零调用者**。
> 该版面的渲染与审批代码**一行未删**，仍是完整可用的死代码。回退入口即可复活，见 v2.2.3。

### 6. `js/app.js` — `openProblemRun(rec, explicitRunId)` 增加第二参数 (line 4891)

**原因**: 刚发起的那次 run，此刻 evidence 可能还没回读到列表里，调用方直接传 run_id 打开。

### 7. `js/app.js` — `runApproval()` 补审批人身份 + 回写问题单 (line 5413-5443)

**原因**: 租户一旦在管理库配了 `approvers` 白名单，名字不在名单里会 403（JWT 模式下由 token `sub` 决定，
body 被忽略）。审批结论需**记录**回问题单（只落 evidence，不执行任何修复动作）。

```js
var by = localStorage.getItem('agentflowApprover') || 'lead-engineer';
agentflowFetch('/runs/' + pcRunId + '/' + action,
  { method: 'POST', body: { node_id: nodeId, by: by, comment: action === 'reject' ? '…' : '' } })
  .then(() => apmApi('/v1/problems/' + record_id + '/run-decision',
                     { method: 'POST', body: { run_id, node_id, approved: action === 'approve', by } })
           .catch(() => {})   // 记录失败不打断审批
  )
```

驳回是**终态**（审批 CAS 不可逆），故走一次 `confirmDialog`；通过保持一键 (line 5823-5831)。

## 踩坑记录

1. **租户头缺失是静默故障**——不带 `X-Tenant-ID` 时 agentflow 回退到 dev 缺省租户，不报错，
   只是 agent 拿不到任何工具。表面上 run 跑起来了、节点也在动，但产出是空转的。
   排查时先确认 run 落在哪个租户。
2. **起 run 的原子性**决定了必须走 APM：绑定与起 run 分开做会留下孤儿 run。
3. **workflow 真源在库不在仓**：`multi-agent-workflow/scripts/problem-log-diagnose.workflow.yaml`
   只是 seed 脚本的推送载荷，改 YAML 不同步到库则 run 跑的还是旧流程，且无任何提示。
