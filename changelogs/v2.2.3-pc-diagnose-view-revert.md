# v2.2.3 — feat: View diagnosis 回到结论版面，执行过程退到弹窗底部「历次执行」区

**日期**: 2026-09-18

**需求背景**: v2.2.2 把「分析new」改走 agentflow 工作流后，`View diagnosis` 的落点被顺带换成了
run 查看器（`#pcRunOverlay`）——点开只剩执行过程，**结论（根因 / 总结 / 修复方案）看不见了**，
而用户看诊断的第一诉求是"结论是什么"。

本版把落点还回结论版面（`.dgx-*`，v1.19~v1.21 的那套），并给执行过程一个新的、不抢主位的位置：
弹窗最下方的「历次执行 · EXECUTIONS」区，点某一行才下钻到那一轮的 run 执行流程。

**关键前提**：结论版面的渲染与审批代码在 v2.2.2 里**一行未删**，只是 `openDiagnosisView()`
失去了调用者。故本版 UI 侧是"重新接线 + 加一个区块"，不是重写。

**配套后端改动**（不在本仓）：`aiops-apm-anomaly-detector` 新增 `aiops_apm/diagnosis/` 适配层，
把 agentflow run 与 spike 快照归一到同一个**诊断视图模型**，`GET /v1/problems/{id}/diagnose`
按记录 evidence 里的绑定分派引擎。UI 因此不需要分辨引擎——这也是本版 UI 改动能这么小的原因。

---

## 改动明细

### 1. `js/app.js` — `view-diagnosis` 落点还回结论版面 (line ~3969)

**原因**: 执行过程不该占据诊断的第一屏；结论才是。

```js
// before（v2.2.2）
else if (act === 'view-diagnosis') openProblemRun(rec); // 分析new 的产物也是一个 run
// after
else if (act === 'view-diagnosis') openDiagnosisView(rec);
```

### 2. `js/app.js` — `openDiagnosisView()` 的守卫放宽 (line ~4275)

**原因**: 原守卫只认 `findDiagnoseSession()`（spike 绑定），新流程记录绑的是 `agent_run`，
会被直接挡掉、弹窗根本打不开。

```js
// before
if (!findDiagnoseSession(rec)) { toast('No diagnosis bound to ...'); return; }
// after
if (!findAgentRun(rec) && !findDiagnoseSession(rec)) { toast('No diagnosis bound to ...'); return; }
```

### 3. `js/app.js` — 表格 `View diagnosis` 按钮的出现条件同步放宽 (line ~3912)

同为上因：`agent_run` 或 `diagnose_session` 任一存在即显示。

```js
var diag = findAgentRun(p) || findDiagnoseSession(p);
```

### 4. `js/app.js` — 新增「历次执行 · EXECUTIONS」区块 (line ~4734 `dgxExecutions`)

**原因**: 执行过程要有入口，但不抢主位。区块列该问题单**每一轮 run**（含打回后重跑），
进行中置顶，点行进该轮的执行流程。

- 数据来自后端视图模型的 `executions[]`（每轮一条，后端已补实时状态）
- 点击经 `#pcDiagnoseBody` 上已有的**委托**处理（`data-exec-run` → `openProblemRun(pcDiagRec, runId)`），
  不新增 `onclick`——沿用本仓「v-html 注入的 HTML 要委托」的约定
- 渲染位置：结论/审批/历史之后，弹窗最下方

### 5. `js/app.js` — 状态头的轮次标识支持两种引擎 (line ~4790)

老记录是 spike 的 `session_id`，新记录是 agentflow 的 `run_id`。视图模型统一落在 `ref`，
`ref_kind` 只影响 title 文案。

```js
((snap.ref || snap.session_id)
    ? '<span class="dgx-chip dgx-mono" title="' + dgxEsc(snap.ref_kind === 'run' ? 'run_id' : 'session_id') + '">' + ...
```

历史快照（`dgxHistSnapshot`）没有 `ref`，自动回落 `session_id`，渲染不变。

### 6. `js/app.js` — 步骤渲染补 `type` 分类与 `verification` (line ~4404 `dgxOptionBody`)

**原因**: 新引擎的修复步骤带 `type`（`code_fix`/`infra_action`/`config_change`）与 `verification`，
老渲染器不认这两个键。补渲染而非丢数据；老快照没有这两个键，逐个判空、不渲染空块。

新增 `DGX_STEP_TYPE` 中文标签映射（复用既有 `.dgx-tag`，**未新增 class**）。

### 7. `js/app.js` — 历史重拉的版本号兼容新引擎 (line ~4290 `pollDiagnosis`)

**原因**: 原来靠 `reanalyze_count`（spike 字段）判断"又推进了一轮"，新引擎没有这个字段
→ 新一轮起来时历史不刷新。

```js
var rev = (typeof snap.reanalyze_count === 'number')
    ? snap.reanalyze_count
    : ((snap.executions || []).length);
```

### 8. `css/styles.css` — `.dgx-exec*` 样式 (line ~7186)

新增 8 个 `.dgx-exec*` 类，**限定在 `.dgx-*` 命名空间**，配色沿用 `.dgx-status--*` 的语言
（进行中蓝 / 完成绿 / 失败红）。使用既有 CSS 变量（`--bg-body`/`--bg-white`/`--border-color`/
`--accent-blue`/`--accent-red`/`--text-tertiary`/`--font-mono`），未引入新变量。

## 踩坑记录

1. **映射必须照运行时真实数据写，不能照 schema 文件**。后端适配层初版照
   `agents/schemas.py` 的 `FixPlanSchema` 写了 fixture，测试全绿——但工作流实际用的是
   `fix-planner`：它的 rca **没有 `summary`**（根因在 `hypotheses[0]`）、plan **多包了一层
   `plan` 键**。结果页面 `conclusion` 整块为 `None`。是拿真实 run 打通后才发现的。
   同一目录并排放着多个 agent 的 schema，**选错文件不会报错，只会静默渲染空白**。
2. **字段名必须照渲染器读的写，不能照"看起来合理"的写**（同一类问题的第二次）。
   「分析链路 · INVESTIGATION」整块数据发空，根因是三个子区块的键名全对不上：

   | 区块 | 渲染器读 | 初版误写成 | 症状 |
   |---|---|---|---|
   | 调研计划 | `t.title` | `t.name` | 每条任务标题空白 |
   | 工具调用 | `ev.status` / `ev.args` / `ev.result_summary` | `summary`（且丢 status/args） | 状态、参数、结果摘要三处全空 |
   | 工具调用（MCP 前缀） | `dgxToolParts` 解析 `mcp__{server}__{tool}` | 只留裸工具名 | 「使用的 MCP Server」整块不出现 |
   | 证据链 | `it.finding` | `it.conclusion` | 每条的「结论」行空白 |

   共同特征：**不抛错、不报 4xx，只是渲染成空白**。真实 trace 里工具信息在 `payload`
   （`result_state`/`input`/`result`），`name` 对 MCP 调用本来就带 `mcp__` 前缀——直接透传即可。
3. **节点字典不含 `name`**：`GET /runs/{id}` 的节点里没有 workflow YAML 写的 name，
   不做 id→中文标签映射，页面上会直接印 `approve-plan`/`know` 这种节点 id 给使用者看。
4. **老版面的死代码是资产不是负债**。v2.2.2 没删它，本版才能只改接线就复活整套渲染与审批。

## 影响范围

| 场景 | 预期 | 实际 | 状态 |
|------|------|------|------|
| 点 `View diagnosis`（新流程记录） | 打开**结论版面**：根因 / 总结 / 修复方案 / 审批 | 接口返回完整视图模型（根因、置信度、1 方案 7 步骤、证据链 3 条） | OK |
| 分析进行中时点开 | 旧版面 + 顶部状态条（分析中 + 已调用 N 次工具） | — | 待浏览器实测 |
| 弹窗底部「历次执行」 | 列出各轮 run，进行中置顶，带实时状态 | 接口返回 2 轮（均 completed） | OK |
| 点「历次执行」某行 | 下钻到该轮 run 的执行流程视图 | 复用既有 `openProblemRun` | 待浏览器实测 |
| 结论版面审批（拒绝/忽略/误报） | 走后端引擎无关决策入口 | 后端已按绑定分派（agentflow / spike） | 待浏览器实测 |
| 老记录（`diagnose_session`） | 走 spike 适配、渲染与改动前一致 | 无老记录可测（当前库内两条均为新流程） | **未覆盖** |
| 历史计划（`dgxPlanHistory`） | 渲染不变 | 历史快照无 `ref`，回落 `session_id` | OK（静态校验） |
| 其余 Actions（Detail / Analyze / Ignore / 分析new） | 行为不变 | — | OK |

- 静态校验：`node --check js/app.js` 通过；新增 class 均有样式定义。
- **未做浏览器端实测**（后端接口层已用真实 run 验证）。老记录路径因库内暂无样本未覆盖。
