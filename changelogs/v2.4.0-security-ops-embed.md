### 4. `tools/tenant_copy.py` — 那场告警风暴按租户替换 (line 94, 229)

**原因（这是本次的**主要缺陷**）**: 该页的 KPI 格「Top alert storm」读的是 `REAL`
（运行期从 `snapshot` 算），而它**正下方**的 case 列表 / agent 活动流 / 对照条
是写死的 best-buy 数据。于是除 best-buy-reference 外的每个租户，一格之内就自相矛盾：

| | 默认租户 otr（修复前） |
|---|---|
| KPI | `INC-MBR-77104 · 159`（动态，对） |
| 正下方 case SEC-1809 | `INC13075702 · 1,809 child events grouped to single root`（写死，错） |

```python
    "sec_storm": "INC13075702",
    "sec_storm_kids": "1,809",
```

```python
    if storm_id and storm_kids:
        pairs.append((LEGACY["sec_storm"], storm_id))
        pairs.append((LEGACY["sec_storm_kids"], f"{storm_kids:,}"))
```

**用裸串而不是整句**：这两串在这一页里每一次出现都指同一场风暴（逐条核对过 ——
事故号 5 处、数字 4 处，含那个渲染成裸数字的 `childEvents` chip）。整句替换只能覆盖
其中一部分，裸串一次全覆盖；两串互不包含，所以顺序无关。

#### ⚠️ 裸串是全站生效的，会一并改到别的页（实测无副作用，但要知道）

`__SIPCOPY__` 是**每页一份、内容同一套**（`inject()` 按租户出表，不按页），
所以裸串不只作用于 Security Ops。实测这两串在别的页上也出现：

|---|---|---|
| `0t1fyt7wcotiz.js`（Service Ops） | `1,809-child storm suppressed by parent gate` | `159-child …`（读起来对） |
| `0t1fyt7wcotiz.js`（Service Ops） | `suppressed 1,809-child fan-out from INC13075702 …` | `suppressed 159-child fan-out from INC-MBR-77104 …` |
| `0wuztp2.9oz~8.js`（数据 bundle） | `cascaded into 1,809 child incidents across WMS, OMS, and Inventory` | 数字跟着租户 |
| `100pim9o6kpoy.js`（Business Ops） | `Canonical example: INC13075702 with 1,809 child incidents` | 同号同数跟着租户 |

### 5. `tools/tenant_copy.py` — case inspector 的「Linked app」(line 967-1020)

**原因（同一类问题，但失败方式更隐蔽）**: case 列表是模块级的静态数组，两条 case
写死了 `appKey:"manhattan wms"`，而 inspector 用
`i.snapshot.apps.find(t=>t.appKey===e.appKey)` 反查 —— 这个 appKey
**只存在于 best-buy-reference 租户**。其余 11 个租户（含默认租户 `otr`）都查不到，
于是渲染时走 `s && (…)` 短路：

```
    s&&(0,t.jsxs)(t.Fragment,{children:[(0,t.jsx)(R,{children:"Linked app"}),…
```

→「Linked app」整块**静默消失**：不报错、不留空态、只是少了那一节。

```python
SEC_APPKEY_FIND = 'appKey:"manhattan wms"'
SEC_APPKEY_REPL = 'appKey:(i.snapshot.topStorm||{}).appKey'
```

这两条 case 讲的就是「Top alert storm」那格 KPI 指向的同一次风暴，所以锚到本租户的
`topStorm.appKey` 语义**完全正确**：点开 KPI、点开 case、Linked app 三处指向同一个 app。

**为什么写成运行期派生而不是静态换字面量**：每个租户的值不同，烤死任何一个都会让其余
11 个错。这里改的是两条 case 的数值来源，不是把某个租户的值写进去。

**为什么安全**（改坏的话整页白屏，比原问题更糟）：
- 位置：`h` 与 `i.snapshot` 在**同一条 `let` 声明**里
  （`let u=i.snapshot.apps…,h=[{…}]`），同一作用域 —— 已用括号配平核过深度；
- 兜底：`(…||{})` 保证 `topStorm` 缺失时得到 `undefined` 而不是抛异常；
- 实测 12 个租户的 `snapshot.topStorm.appKey` **全部存在**，兜底只是保险。

**不动的**：其余三条 case 的 appKey（`anchor-app` / `order management` /
`enterprise teradata` / `repair workbench`）在**任何**租户里都不存在，没有语义对得上
的映射可做 —— 硬凑成别的 app 就是编数据，所以保持原样（那几条的 Linked app 仍不显示）。

## 踩坑记录

### A. 下载的页面是 DOM 快照，不能当入口（skill 已警告，本次再次确认）

`~/Downloads/Service Intelligence Platform · Accenture.html` + `_files/` 是 Chrome
「网页，完整」保存的产物。实测服务器原始外壳里 `self.__next_f` 7 处，而保存版是
React 渲染完的静态 DOM。**只能当资源来源**，入口必须用 `--refresh` 拉。
本次只有 1 个 chunk（`15zvtls0y9kdc.js`）不在仓内分享池里，它在下载目录里也有 ——
两边 `cmp` **逐字节相同**，所以没有「旧 chunk 配新外壳」的版本错配。

### B. ★ 自检脚本漏掉了本次最要紧的写死数据

`check-embed-wiring.py` 的 `scan_fixed_copy()` 用
`ESTATE_NOUN = \b(apps|portfolios|journeys|teams|nodes|incidents)\b` 找「数字 + 房地产名词」。
**`INC13075702` / `1,809` 一条都没报** —— 因为「1,809 child events」里的 `child events`
不在名词表里。是人工读 chunk 才发现的。

**这个漏检的代价**：如果只信脚本的 `✓ 接线完整`，就会漏掉「KPI 与正下方 case 自相矛盾」
这个用户一眼能看见的问题。接下一页面时不要只跑脚本。

### C. ★ 写死的 appKey：失败方式是「整节静默消失」

`scan_fixed_copy()` 也扫不到它（`appKey:"manhattan wms"` 没有数字）。
而且它比文案更隐蔽 —— 文案错了是「说了错话」，appKey 落空是「那一节不见了」，
既有代码写的是 `s && (…)`，不报错、不留空态。

**通用判据**（已回写进 CLAUDE.md）：拿该页的写死值去**逐个租户的快照里查一遍**。
本次一查就发现 5 个 appKey 里有 4 个在 11/12 个租户里都不存在。

### D. `innerText` 会套 `text-transform`，验证脚本别按原大小写找

用 CDP 验证点击时，面板标题在 DOM 里是 `Case inspector`，但 `innerText` 返回的是
`CASE INSPECTOR`（CSS `text-transform: uppercase`）。按 `indexOf('Case inspector')`
匹配会**假阴性**——看起来像「点击没生效」，实际是找错了串。
