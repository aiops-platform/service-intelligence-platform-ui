# v1.19.0 — feat: Problem Center 新增「分析new」动作：一条问题单 → 一键触发 HolmesGPT 诊断，session_id 绑回问题单并在页面内展示诊断内容

**日期**: 2026-09-10

**需求背景**: Problem Center 已有「Analyze」（选 agentflow workflow → POST /run → 跑 Bug Solve 工作流）。现需要**另一条独立入口**：
针对一条问题单，直接调用 **HolmesGPT 诊断服务**（spike：`aiops-agent-orchestration-spike`，`POST /diagnose/logs`），
由**后端**按该问题单**拼装**诊断请求（日志摘录 + app + repo + trace_id），拿到 `{session_id, status:"analyzing"}` 后
**把 session_id 绑定到这条问题单**；前端据此把按钮置灰（不可重复点击），并提供**页面内查看诊断内容**（轮询直到终态）。

与既有 Analyze **并存、互不影响**：Analyze 会翻 `state=in_progress` 并跑 agentflow 工作流；「分析new」**不翻 state**，
只在该问题单 evidence 追加一条 `diagnose_session`，作为「已发起诊断」的绑定真源。

## 改动明细

### 1. `js/app.js` — Problem Center（`initProblems`）

- **actions 列**（`renderTable`）：在 `Detail` 后新增
  - `<button data-act="diagnose">分析new</button>`：`state` 为 `pending`/`in_progress` 时显示；**已绑定诊断 → `disabled` + title 提示**（不可再点击）；
  - `<button data-act="view-diagnosis">View diagnosis</button>`：**已绑定诊断**时才出现。
  原有 Analyze / Ignore / View analysis 逻辑不动。
- **点击分派**：`data-act="diagnose"` → `startDiagnose(rec)`；`data-act="view-diagnosis"` → `openDiagnosisView(rec)`。
- **`findDiagnoseSession(rec)`**：从 `rec.evidence` 取最新一条 `{type:"diagnose_session", session_id}`（record_id → session_id 的桥，
  与既有 `findAgentRun` 同源思路）。
- **`startDiagnose(rec)`**：`POST /v1/problems/{id}/diagnose`（body `{}`，字段全由后端拼装）→ 成功 toast 带 session_id，
  然后 `refresh()` **以后端 evidence 为准**（非乐观）→ 按钮自动置灰、出现 View diagnosis。带 `diagBusy` 防双击。
- **诊断内容视图**（`#pcDiagnoseOverlay`）：`openDiagnosisView` → 立即拉一次 + **每 2s 轮询**
  `GET /v1/problems/{id}/diagnose`（后端同源代理诊断服务 `GET /status/{session_id}`），到终态
  （`completed`/`failed`/`approved`/`closed_manual`）停轮；关闭弹框 / Escape / 点遮罩清 timer。
- **诊断内容渲染（`.dgx-*`，diaGnosis eXperience）——结论优先的信息层级**：

  | # | 分区 | 说明 |
  |---|------|------|
  | 头部 | 状态头（吸顶） | 状态胶囊（analyzing/completed/failed…）+ 来源 trigger / session_id / 耗时 chip + 更新时间 + 问题标题 |
  | — | 运行中进度 | 未到终态时显示 spinner +「已完成 N 次工具调用」 |
  | 1 | 根因 · ROOT CAUSE | 视觉重心卡片（左侧紫色竖线）；**同屏**给出置信度胶囊（高/中/低，着色）与 deployed/base/已修复于 短 SHA chip、base_note |
  | 2 | 总结 · SUMMARY | 纯文本段落 |
  | 3 | 修复方案 · FIX OPTIONS | **单方案直接铺开**；**互斥多方案 → 分页签**（`方案1..N`，推荐项带 ★，默认选中 `dgxOptSel`）。每步渲染 action/target/risk 标签、change、预期效果、回滚、`suggested_diff` 代码块 |
  | 4 | 分析链路 · INVESTIGATION | `<details>` **默认关闭**；标题右侧摘要（调研计划 N · 工具调用 N · MCP server N · 证据 N）。展开后：**调研计划**（tasks 状态点）→ **使用的 MCP Server**（按 `mcp__{server}__{tool}` 前缀聚合 + 调用次数徽标）→ **工具调用时间线**（tool/MCP 标签 + 参数 + result_summary）→ **证据链**（source/commit/查询/结论，原文二级折叠）→ **原始 JSON** 兜底折叠 |

  所有文本经 `escapeHtml`。交互状态 `dgxOptSel`（方案页签）与 `dgxChainOpen`（链路开合）在 `openDiagnosisView` 复位，
  保证换记录不串数据；轮询重渲染时按状态回填，交互不丢失。

  **调研计划的任务状态：一律中文标签 + 终态派生（不再印原始枚举）。** 背景：`tasks` 是模型自报账本
  （只有 `complete_task` 工具写 `done`），而最终结论走的是另一条通道（runner 解析模型最后一条 JSON），
  于是「收敛根因并给出修复方案」这类收尾步骤永远没人置 done——**诊断已完成、结论和修复方案都在，
  分析链路里那一步却是 `todo`**。修法分两层：

  - **服务端（spike，已随本版一起改）**：`finalize_terminal_tasks` 在落终态时做确定性归一，
    契约是 **「终态 ⇒ 不留 todo/in_progress」**——`completed`/`approved` → `done` + `derived=True`；
    `failed`/`closed_manual` → `cancelled`（**绝不置 done**，不伪造完成）。详见 spike
    `docs/TRACE_CODE_DESIGN.md` §3.1。
  - **前端（本文件，显示侧兜底）**：`dgxTaskView(snap, t)` 把枚举映射为
    `todo→待办`、`in_progress→进行中`、`done→已完成`、`failed→失败`、`cancelled→已中止`，
    并复用/新增 CSS 修饰类（`in_progress→.dgx-task--running`、新增 `.dgx-task--cancelled`）。
    **会话已到终态却仍见 `todo`/`in_progress`（旧会话或服务端未归一的异常路径）时按同一契约派生**：
    有结论 → 「随结论完成」（`.dgx-task--done.is-derived`，灰显 + title 说明「未显式标记完成，随结论一并收口」）；
    无结论（failed/closed_manual）→ 「已中止」（灰点 + 标题删除线）。非终态照常显示待办/进行中。
    这样即使后端还是旧版本，页面上也不会出现「已完成却显示待办」。

### 2. `index.html` — 新增 `#pcDiagnoseOverlay` 诊断内容弹窗

  尺寸**不在行内写死**（交由 CSS 与 View analysis 对齐）。

### 3. `css/styles.css` — 弹窗尺寸对齐 + `.dgx-*` 作用域新样式

- **弹窗尺寸与 View analysis（`#pcRunOverlay`）一致**：`max-width: 1280px`、`height/max-height: calc(100vh - 120px)`、
  遮罩 `padding: 60px 28px` + 垂直居中。因弹框自身定高，`.pc-diag-body` 去掉 `max-height: 72vh`（滚动交给 `.ap-modal-body`）。
- **布局适配宽弹框**：`.dgx` 内容列 `max-width: 1120px; margin: 0 auto`（居中、限制行宽，卡片不被拉满 1280）。
- 吸顶状态头、状态/置信度/风险着色、卡片与分区标签（`· LABEL` 大写小字）、修复方案分页签 + step 左竖线 +
  risk/rec 徽标 + code 块、分析链路 `<details>` 折叠 + caret 旋转 + MCP 徽标 + 工具时间线 + 证据卡片 + 二级折叠。
  均限定在 `.dgx-*`，不影响其他页面。仅保留 `.pc-diag-body / .pc-diag-loading / .pc-diag-error`（加载与失败态）。

**修复（E2E 实测发现）**：`.dgx-head` 原先用 `<header>` 标签，命中全局顶部菜单栏规则
`header { height: 52px; position: fixed; box-shadow: …; padding: 0 16px; }` —— 高度被锁死 52px 而标题
（问题标题 `[log] …`）溢出块外约 7px，**直接压在「根因」卡片上**（即「标题离根因太近」的真因）。
改为 `<div class="dgx-head">` 并补 `box-shadow` 吸顶柔和投影、`padding-bottom` 10→12px。

|------|------|------|
