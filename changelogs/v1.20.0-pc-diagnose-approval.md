# v1.20.0 — feat: View diagnosis 新增「审批动作 + 历史计划」：拒绝重跑 / 忽略关单 / 误报关单，历史计划落问题单详情最下边

**日期**: 2026-09-10

**需求背景**: v1.19.0 已把「一条问题单 → 诊断服务 → 拿到结论 + 多方案」在页面内跑通，但**看完结论之后没有地方下判断**：
选中的方案没有"就按这个办/不办"的出口，也无法把这条问题单关掉。本版补上**人对结论下判断**这一段，共四个动作：

| 动作 | UI 按钮 | 语义 |
|---|---|---|
| 拒绝 | `拒绝 · 重新分析`（需填修改建议） | 方案不对/不认可 → 把建议回灌 → **整个诊断重跑**，产出新一版修复方案 |
| 忽略 | `忽略`（二次确认） | 不需要做 → **关掉这条问题单**（`state=closed`） |
| 误报 | `误报`（二次确认） | 判定为误报 → 记一次误报率 + **关掉**（`state=resolved`） |
| 通过 | —（**本版不做**） | 已明确：spike 的 `/approve` decision=approve 是**终态签章、无下游执行器**，本版不出现在 UI 上 |

弹窗**最下边**新增「历史计划 · PLAN HISTORY」：每一次被拒的方案（含当时步骤与拒因）都留档展示。

**跨三仓改动**：UI（本仓）→ APM（`aiops-apm-anomaly-detector`）→ spike（`aiops-agent-orchestration-spike`）。

**关键设计取舍（决定了架构）**：

1. **历史计划存在 APM 的 `problem_record.evidence`，不在 spike。** 因为 spike 的 `session.remediation` 是**单值**的，
   且每次重跑 `run_diagnose` 都会 `remediation = None` + `conclusion = None`（`runner.py:120-121`）——
   **旧计划在 spike 侧必丢**。问题单的 `evidence`（JSON 列）是唯一能承载历史的持久真源。
   因此**另开一个只读端点** `GET /v1/problems/{id}/diagnose/decisions` 读历史，
   **不改** `GET /v1/problems/{id}/diagnose` 的响应形状（它必须保持"逐字回传 spike 快照"，UI 直接读顶层字段）。
2. **忽略 = `closed`、误报 = `resolved` + FPR**：复用既有 FPR 回写链路（`_record_fpr`），
   `closed` 是**与 `resolved` 并列的另一个终态**——`open_group_key` 生成列只认 `pending/in_progress`，
   故 `closed` 自动退出 UNIQUE 约束、**允许同类问题复发时开新单**。**无需 DDL 迁移**
   （`V1__init_tables.sql:17` 的注释已含 `closed`）。
3. **忽略/误报不能被会话过期卡住**：spike session 是内存态 + TTL，过期即 404。
   若因 404 就失败，就重现了此前抱怨过的"404 死胡同"——所以 APM 对 `/dismiss` 的 404 **容忍并继续关单**
   （仅记 `session_status="expired"`）。而**拒绝必须要求会话还活着**（会话没了就没东西可重跑 → 409）。

## 改动明细

### 1. spike `aidiag/api.py` — 新增唯一新端点 `POST /dismiss/{session_id}`

在 `/approve` 之后插入（紧随其后、`/health` 之前）：

```python
class DismissRequest(BaseModel):
    reason: str = ""

@app.post("/dismiss/{session_id}")
async def dismiss(session_id: str, req: DismissRequest | None = None) -> dict[str, Any]:
    """忽略/误报：把会话签为终态 dismissed（不改 conclusion、不重跑、不碰 tasks）。"""
```

- 只接受已收敛的会话（`completed` / `failed` / `closed_manual`）；`analyzing` → **409**（先 `/stop`）；
  已 `dismissed` → **409**（语义明确，不静默成功）；未知 / 过期 → **404**。
- reason 追加进现成的 `session.feedbacks`（不为一个字符串新加字段）。
- **不调 `finalize_terminal_tasks`**：dismiss 不重跑，`tasks` 在 `completed` 时已归一
  （或本就是 `failed` 的 `cancelled`）——再归一反而会把 `cancelled` 弄脏。
- **不动** `/remediate`、`/approve`、`_resolve_specs_for`、`session.py`（`status` 是自由 `str`，
  `snapshot` 已回传 `status`/`feedbacks`，无需新字段）。

### 2. spike `tests/test_dismiss.py` — 新增 10 例（纯离线）

`completed`/`failed`/`closed_manual` 可 dismiss；空 reason 不落 `feedbacks`；`analyzing` → 409；
重复 dismiss → 409；未知 id → 404；**dismiss 不改 tasks**（`completed` 会话的 `done`+`derived` 保持原样、
`failed` 会话的 `cancelled` 不被改写）；一条 HTTP 往返冒烟。

### 3. APM `src/aiops_apm/storage/records.py` — 新增 `RecordStore.close()`

- ABC 增加抽象方法（紧跟 `resolve` 之后）；`InMemoryRecordStore.close` 镜像同文件 `resolve`：
  `state="closed"` + `resolved_at=now(utc)` + `resolve_reason=reason`；
  `MySQLRecordStore.close`：`UPDATE problem_record SET state='closed', resolved_at=NOW(3), resolve_reason=%s
  WHERE tenant_id=%s AND record_id=%s AND state <> 'closed'`。
- **复用既有审计列**（`resolved_at` / `resolve_reason` 本就是通用的"关闭时间/原因"，`closed` 同样适用）→ **零迁移**。

### 4. APM `tests/test_records.py` — 扩充 3 例

`close()` 落 `closed` + 审计列；**`closed` 后 `find_open` 不再命中 → 同类复发可开新单**；
缺失 / 跨租户为 no-op。

### 5. APM `src/aiops_apm/router/problems.py` — 抽 FPR 助手 + 决策门 + 历史读取

- **(a) 抽 `_record_fpr(storage, tenant, rec, *, false_positive)`**（纯重构、零行为变化）：
  把 `resolve_problem` 里 `write_fpr + load_fpr + update_fpr_gauge` 那段抽出，
  `resolve_problem` 改为调用它（保留"body 缺省为假时也记一次有效判定"的既有语义）。
- **(b) 请求体** `DiagnoseDecisionBody`：`decision ∈ {reject, ignore, false_positive}`、
  `feedback: str = Field("", max_length=2000)`、`option_index: int | None = None`（**1-based**，缺省 → spike 侧推荐方案）。
- **(c) `POST /v1/problems/{record_id}/diagnose/decision`**：
  - 守卫：记录不存在 → 404；`state ∈ {resolved, closed, archived}` → 409（镜像 `diagnose_problem` 的终态守卫）；
    未绑定诊断会话 → 409（**零出站**）；
  - `reject`：`feedback.strip()` 为空 → 400 `VALIDATION`（"拒绝必须带修改建议"、**零出站**）→
    先 `POST {base}/remediate/{sid}` `{option_index}`（**从响应取 `steps/option_title/option_index` 存进 evidence
    —— 这是历史计划的唯一留存处**）→ 再 `POST {base}/approve/{sid}` `{decision:"reject", feedback}` →
    取 `remediation_status / reanalyze_count / max_reanalyze`；**问题单 state 不变**（重跑中）；
    spike 404 → 409「诊断会话已过期，无法重跑」；其他非 2xx → 502 `UPSTREAM`。
  - `ignore` / `false_positive`：`POST {base}/dismiss/{sid}` `{reason}` →
    **404 容忍**（记 `session_status="expired"`，继续关单）；其他非 2xx → 502；成功 → `"dismissed"`。
    `false_positive` 先 `_record_fpr(..., false_positive=True)` 再 `records.resolve(reason="false_positive")`；
    `ignore` 直接 `records.close(reason="ignored")`。
  - 每次落一条 evidence（统一形状，无关字段为 `null`）：
    `{type:"diagnose_decision", decision, session_id, option_index, option_title, steps, feedback,
    session_status, remediation_status, reanalyze_count, max_reanalyze, decided_at}`；
    返回 `{record_id, decision, session_id, session_status, remediation_status, reanalyze_count,
    max_reanalyze, record_state}`。
- **(d) `GET /v1/problems/{record_id}/diagnose/decisions`** → `{"items": [...]}`：
  按 `evidence` 里 `type=="diagnose_decision"` 过滤、按写入顺序返回；**不加状态守卫**（只读，供 UI 渲染历史）；
  记录不存在 → 404。
- 出站纪律全部沿用现有写法：`OutboundGateway.validate_url(url)` + `httpx.HTTPError → AppException(UPSTREAM)`
  + `resp.status_code >= 300 → 502`。

### 7. UI `js/app.js` — 审批条 + 历史计划

- **常量与弹窗态**（`initProblems` 内，与 `dgxOptSel`/`dgxChainOpen` 同规矩、**全部在 `openDiagnosisView` 复位**）：
  - `PC_DIAG_TERMINAL` 增加 `dismissed: 1`；
  - 新增 `DGX_STATUS_LABEL`（`analyzing→分析中 / completed→已完成 / failed→失败 / approved→已通过 /
    closed_manual→需人工处理 / dismissed→已忽略`）——状态胶囊**改印中文标签**，CSS 类仍用原始
    `dgx-status--<en>`（不破坏着色），兜底 `|| st`。沿用 `dgxTaskView` 已确立的「**绝不把原始枚举印给用户**」纪律；
  - `dgxFbOpen` / `dgxFbText`（拒绝反馈框开合与文本，轮询重渲染回填）/ `dgxDeciding`（POST 在途，按钮 disabled）/
    `dgxRerunPending` + `dgxRerunCount`（拒绝后抑制旧快照）/ `pcDiagHistory`。
- **`ensureDiagPolling()`**：`stopDiagPolling(); pcDiagTimer = setInterval(pollDiagnosis, 2000);`
  —— `openDiagnosisView` 与拒绝成功后共用。
- **审批条 `dgxApproval(snap)`**（插在 `dgxFixOptions` 之后、`dgxChain` 之前）：
  - 显示条件：`record.state ∈ {pending, in_progress}` **且** `snap.status ∈ {completed, failed, closed_manual}`
    **且** `!dgxRerunPending`（`dismissed`/`approved`/`analyzing` 不显示；已 resolved/closed 的记录不显示
    → **不会出现"点了报 409"的死按钮**）；
  - 内容：`当前待处理：方案N「title」`（取 `conclusion.recommended_fix[dgxOptSel]`，多方案提示去上方切页签）
    + 三个按钮 `拒绝 · 重新分析`（`.dgx-btn--reject`）/ `忽略`（`.dgx-btn--ignore`）/ `误报`（`.dgx-btn--fp`）。
    拒绝按钮**仅在选中方案有 `steps` 时可用**（否则 disabled + title，与 spike `remediate` 的 409 对齐）。
- **`submitDiagnosisDecision(decision)`**：`dgxDeciding=true` →
  `POST /v1/problems/{id}/diagnose/decision` body `{decision, feedback: dgxFbText, option_index: dgxOptSel + 1}`：
  - **reject 成功**：toast 带 `reanalyze_count/max_reanalyze`（达上限提示"需人工处理"）；
    `dgxRerunCount = resp.reanalyze_count`、`dgxRerunPending = !capped`（`capped = remediation_status === 'closed_manual'`）、
    清反馈框；**重启 2s 轮询 + 立即 `pollDiagnosis()`**；顺手刷新历史。
  - **ignore / false_positive 成功**：toast → `closeDiagnosisView()` + `refresh()`（问题单已关，列表以后端为准）。
  - **失败**：toast(`err.message`) 并 `dgxDeciding=false`，弹窗保持（可改建议重试）。
    `apmApi` 已把后端 `{code,reason}` 的 `reason` 提成 `err.message` → 409/400 的中文原因直接展示。
- **拒绝后抑制旧快照**：`_schedule_run` **不会同步**把 `session.status` 置 `analyzing`（只有后台 `run_diagnose` 才置）
  → 拒绝的响应里 `session_status` 是旧值 `completed`。若照旧渲染，会立刻重新出现"可再次点拒绝"的按钮
  （spike 侧 plan 已 `rejected` → 409）。故在 `dgxRerunPending` 期间 `renderDiagnosis` 只更新状态头 +
  显示「已提交修改建议，正在重新分析…」，**不渲染审批条**；`pollDiagnosis` 回调里当
  `snap.status === 'analyzing'` **或** `snap.reanalyze_count > dgxRerunCount` 时清该 flag
  （覆盖"重跑太快没观察到 analyzing"）。
- **历史计划 `dgxPlanHistory()`**（**详情最下边**）：`loadDiagnoseDecisions(recordId)` →
  `GET /v1/problems/{id}/diagnose/decisions` → 存 `pcDiagHistory.items` → 重新渲染；
  调用点 = `openDiagnosisView`（复位后拉一次）/ 拒绝成功后 / `pollDiagnosis` 里检测
  `snap.reanalyze_count !== pcDiagHistory.rev`（别的操作者改了）时。
  渲染 `only if items.length`：每条一个 `<details>`——`summary` 是 `#序 方案N · option_title` +
  决策胶囊（`已拒绝`/`已忽略`/`已误报`）+ `decided_at`；展开是**拒因**（`feedback`）+ **该版计划的步骤**
  （直接复用 `dgxOptionBody({title, steps})`，自动带 action/target/risk、change、预期效果、回滚、
  `suggested_diff`）+ 页脚 `驳回次数 reanalyze_count/max_reanalyze`（`closed_manual` 时补"已达驳回上限，需人工处理"）。
- **`dgxOptionBody` 头部改条件渲染**（`if (o.title || o.recommended)`）：历史条目只传 `{steps}` 时不再印空标题头。
- **事件委托扩展**（`#pcDiagnoseBody`）：`click` 先认 `.dgx-act`（`data-act="reject"|"reject-submit"|"reject-cancel"|
  "ignore"|"fp"`）再认 `.dgx-tab`（`.dgx-tab` 与 `dgxOptSel` 写回**不动**）；`input` 认 `.dgx-fb-input` → 写 `dgxFbText`
  （轮询重渲染不丢输入）；`toggle`(capture) 仍只认 `.dgx-chain`（历史条目默认收起，无需记开合态）。
