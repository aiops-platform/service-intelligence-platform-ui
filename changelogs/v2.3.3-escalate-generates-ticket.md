# v2.3.3 — 处理模块：「误报」换成「升级 · 生成工单」，问题单一键转 escalated

**日期**: 2026-09-21

**需求/背景**: 「我形成了 plan 或者是我通过根因分析后，觉得不是一个问题，那么就会到 approve plan
这个节点，但是我现在这个节点想要换成：Diagnosis output，会在 view Diagnosis 页面的处理模块中，
还是有 拒绝 · 重新分析、忽略、升级，如果是我点击忽略，就直接忽略，如果是升级，那么直接就相当于
这个节点审批通过，会到下一个节点，就是创建一个 ticket，然后返回一个 ticket 号绑定到这条数据中。
然后成功生成 ticket 了之后，那么状态就变成一个生成成功的状态。」

后端（`aiops-apm-anomaly-detector`）同批把诊断输出门的第三种裁定做成了
`POST /v1/problems/{id}/diagnose/decision {decision: "escalate"}`：放行 agentflow 的审批门 →
在 agentflow 建一张修复工单（`INC-YYYYMMDD-NNNN`）→ 工单号绑进 `evidence` →
问题单 `state` 转 `escalated` 终态。本仓这一版把入口接上。

**为什么「升级」顶掉的是「误报」（见「未处理」第 1 条）**：处理模块要维持三个按钮。

## 改动明细

### 1. `js/app.js:4904` — `dgxApproval()`：`canEscalate` 的判据

```js
// 升级 = 认可诊断 → 平台建一张修复工单。**判据是"诊断给出了方案"，不是"选中那份方案完整"**：
// 要派的是整份诊断，与用户当前翻到哪个分页签无关。
var canEscalate = (st === 'completed') && opts.length > 0;
```

**为什么不用 `snap.approval.available`**（后端 viewmodel 里确实有这个字段）：它只在
`pending_approvals` 非空时为真，**审批一旦被答复就变 false**——而那正是"run 已经跑完、
就等你决定"这个真正要用的时刻，用它当显隐条件按钮会自己消失。

**为什么还要卡 `opts.length > 0`**：`st === 'completed'` 对 **halt 中断的 run 也成立**
（run 状态是 `success` → 映射成 `completed`，`outcome=halted` 前端拿不到），而 halt 路径下
`plan` 节点是 SKIPPED、诊断根本没有方案——不卡就会从一份没有方案的诊断里建出工单。
卡上之后，下面那句 hint「本次诊断未给出可执行方案，仅可忽略。」与按钮的显隐**逐字一致**。

### 2. `js/app.js:4929` — 按钮：顶掉「误报」的位置（最右），布局不变

```js
'<button ... class="dgx-btn dgx-btn--ignore dgx-act" data-act="ignore" ...>忽略</button>' +
(canEscalate
    ? '<button ... class="dgx-btn dgx-btn--escalate dgx-act" data-act="escalate" ...>升级 · 生成工单</button>'
    : '') +
```

不可用（没方案）时**不渲染**，而不是渲染成 disabled——与既有的 `canReject` 同款，
且 hint 已经说明了原因（不会出现"按钮为什么是灰的"这种疑问）。

### 3. `js/app.js:4970` — `dgxApproval()` 开头：已升级 → 处理卡换**结果卡**

```js
if (recState === 'escalated') {
    var hist = (pcDiagHistory && pcDiagHistory.items) || [];
    var esc = null;
    for (var k = hist.length - 1; k >= 0; k--) {
        if (hist[k] && hist[k].decision === 'escalate') { esc = hist[k]; break; }
    }
    var no = (esc && esc.ticket_number) || '';
    return '<section class="dgx-card dgx-approve">…已升级——本次诊断已转成一张修复工单' +
        (no ? '，工单号 <span class="dgx-mono">' + dgxEsc(no) + '</span>' : '') + '。</div></section>';
}
```

单号取自**历史**（真源 = 后端 evidence），不是本地记的临时值：重开弹窗、换台机器看到的一样。
历史是异步拉的，所以首次渲染可能先无号，拉完由 `loadDiagnoseDecisions` 里的
`renderDiagnosis` 补上。

### 4. `js/app.js:4980` — `submitDiagnosisDecision()`：第三条出口

原来是两条（reject → 重跑、其余 → 关弹窗）。escalate 是第三条，**弹窗留着**：

```js
} else if (decision === 'escalate') {
    var num = (resp && resp.ticket_number) || '';
    window._showToast(num ? ('已升级，工单 ' + num + ' 已生成') : '已升级，工单已生成', 'success');
    // ⚠️ **必须就地翻本地 state**
    pcDiagRec.state = 'escalated';
    loadDiagnoseDecisions(recordId);
    pollDiagnosis();
    refresh();
}
```

**为什么必须就地翻 `pcDiagRec.state`**（这是最容易漏的一步）：处理卡的显隐读的就是它
（`dgxApproval` 开头），而 `pollDiagnosis` 只重拉诊断快照、**不重拉 record**
（`pcDiagRec` 只在 `openDiagnosisView` 里赋值），`refresh()` 也不回写它。
不翻的话升级后那张卡照旧显示、三个按钮全是活的，再点「忽略」会撞上后端新加的
`escalated` 终态守卫拿 409——一个不该存在的死按钮。

**为什么还要显式 `loadDiagnoseDecisions`**：`pollDiagnosis` 只在该快照的 `rev` 变化时才重拉历史，
而 agentflow 路径下 `rev = executions.length`；**升级不新增 run → rev 不变 → 不会重拉**，
工单号就永远不出现。

### 5. `js/app.js:4671` — 决策标签表补 `escalate`

```js
var DGX_DECISION_LABEL = { reject: '已拒绝', ignore: '已忽略', escalate: '已升级', false_positive: '已误报' };
var DGX_DECISION_CLS   = { reject: 'reject', ignore: 'ignore', escalate: 'escalate', false_positive: 'fp' };
```

漏登记会被 `dgxPlanHistory` **原样把枚举印给用户**、chip 兜底成灰色。
`false_positive` **保留**：后端枚举里还有它（M7 的误报回写链路在用），历史里仍会出现。

### 6. `js/app.js:5261` — 历史计划条目显示工单号

### 7. `js/app.js:4027` + `legacy-panels.html:1025` + `styles.css:4957` — 新终态的三处成对

```js
var STATE_FILTERS = ['all', 'open', 'in_progress', 'resolved', 'closed', 'escalated'];
```
```html
<button class="filter-chip pc-state-filter" data-filter="escalated"><span class="chip-dot" style="background:#8b5cf6;"></span> Escalated</button>
```
```css
.alert-tag.status-escalated  { background: #f5f3ff; color: #7c3aed; }
```

**三处缺一不可**：`STATE_FILTERS` 少了 → `/problems?state=escalated` 被 URL 白名单静默丢弃；
chip 少了 → 筛得出来但没有任何控件能切到它；CSS 少了 → **不报错**，只是白底黑字像漏了样式
（`.alert-tag` 基类没有背景色兜底）。

`problemDisplayStatus()` **不用改**：未知 state 原样透传，所以 `state='escalated'` 一回来，
表格状态列与详情弹窗头部立刻显示 `escalated`。配色用紫而非绿：escalated 是"派出去等别人做"，
与 Resolved（已好了）的绿一眼分得开。

`renderKpi()` **不用改**：它只把 `pending|in_progress` 计 Open、`resolved` 计 Resolved——
`escalated` 与既有的 `closed`/`archived` 一样两边都不落，行为一致。

### 8. `js/app.js:6341` — 事件委托：`fp` 分支换成 `escalate`

```js
} else if (act === 'escalate') {
```

二次确认与「忽略」同款：这一步会把问题单转终态、且**会真的建出一张工单**，误点代价更高。

## 未处理

1. **「误报」的 UI 入口没了，FPR 回写链路只剩自动判定这一条来源。**
   `data-act="fp"` 全仓只在这一处；`_record_fpr` 只被 `/resolve{false_positive:true}` 与
   `_decide_agentflow` 的 false_positive 分支调用，而表格行的 Actions 只有
   Detail / Analyze / View diagnosis / Ignore——**没有别的界面入口**。
   这是「三个按钮」的必然代价（已与需求方确认取舍）。要补回来的话，最省的位置是
   Problem Detail 弹窗里加一个「标记误报」按钮（走 `POST /{id}/resolve{false_positive:true}`）。
2. **升级的二次确认文案是平台语言，不是用户语言**（含 `escalated` 这个枚举词）。
   它与「忽略」那句「忽略该诊断并关闭这条问题单？」风格一致，但枚举词漏进了 UI。
3. **`dist/` 未重建**（`.gitignore` 忽略，部署时 `npm run build` 会由
   `vite.config.js` 的插件把 `js/app.js` 复制过去）。开发环境 Vite 直接把源文件当 classic
   script 伺服，无需构建。
