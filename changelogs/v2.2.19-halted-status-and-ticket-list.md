# v2.2.19 — 以 halt 结束的流程不再算成功；Ticket 列表状态改为从 run 派生

**日期**: 2026-09-20

**问题/背景**: 两件事，同一类根因 —— **界面把"跑完了"当成了"有结果"**。

1. 停在 halt 节点的 run，前端显示成绿色的 `success`，节点显示成 `done`。
2. Ticket Inbox 里，流程早就跑完了，状态还一直挂着 `running`。

---

## 一、halt 的 run 不是成功

### 后端已经给了判据，前端没用

`GET /runs/{id}` 早就返回两层的判定：

| 字段 | 含义 |
|---|---|
| `status` | **有没有节点失败**。中断的 run 没有节点失败（halt 节点自己 DONE、其余 PENDING 全部 SKIPPED）→ 仍是 `success` |
| `outcome` / `halted_at` | **按图走完**（`completed`）还是**中途证据不足**（`halted`），停在哪个节点 |

前端此前**只读 `status`**（`grep outcome src/` 零命中），于是"证据不足、什么都没诊断出来"和"顺利跑完"在界面上长得一模一样。

### 改动明细

#### 1. `src/utils/runStatus.js`（新增）

判据与配色收在一处。三个消费面（图画布、节点表、详情徽章）各写一遍会得到
「图是绿的、表写 done、徽章说中断」这种自相矛盾的界面。同时导出
`NODE_STATUS_CLASS` / `statusClass` —— 那张表原先住在 `useBugSolveRun.js`。

```js
export const HALTED = 'halted'
export function runStatusOf(run)     // outcome=halted → 'halted'，否则 run.status
export function nodeStatusOf(run, nid, raw)  // 只有 halted_at 那个节点改报 halted
```

#### 2. `src/views/bug-solve/useBugSolveRun.js` — 表搬家 + 原样再导出

```js
export { statusClass } from '@/utils/runStatus'   // 两个调用方不动
```

新增 `runMeta` 存 `{outcome, halted_at}`（原先只存 `runStatus = data.status`）。

#### 3. `src/views/runs/useRunDetail.js` — `displayStatus` 与 `status` **分开**

```js
const status = computed(() => run.value?.status || '')          // 判终态/轮询用
const displayStatus = computed(() => runStatusOf(run.value))    // 只有渲染用
```

**必须分开**：`TERMINAL` 集合里没有 `halted`，拿展示值去判终态，轮询就永远停不下来
（终态 run 会被 2 秒一轮反复拉）。

#### 4. `RunDetailView.vue` / `BugSolveView.vue` — 三处渲染改用派生值

#### 5. `css/styles.css`

```css
.bs-node-status-halted .bs-node-rect { fill: #fffbeb; stroke: #d97706; stroke-width: 1.6; }
.bs-node-status-halted .bs-node-text { fill: #92400e; }
.bs-badge-halted    { background: #fffbeb; color: #92400e; }
.alert-tag.status-halted { background: #fffbeb; color: #b45309; }
```

**琥珀而不是红**：红是"失败"，中断不是失败，是**需要人补信息**。

## 二、Ticket 列表一直是 running

### 根因：工单状态从 run 开始后没有任何代码再写它

```python
# api/app.py:735 —— 全仓唯一的 set_status 调用
await tickets.set_status(ctx.tenant_id, tid, TICKET_RUNNING)
```

`TICKET_RESOLVED` / `TICKET_FAILED` 在 `ticket_store.py:54-55` 定义了，但
**全仓没有任何地方写入**。run 成功、失败、中断都不回写 —— 所以列表读到的永远是
发起那一刻写下的 `running`。改前 21 条工单里 14 条 "In Progress" **全是假的**。

### 改动明细

#### 6. 后端（`multi-agent-workflow`）：`GET /tickets` 附 `latest_run`

`api/app.py` 新增 `_with_latest_run()`：只对 `status == running` 的工单取
`run_ids[-1]`，读它的 run + nodes + snapshot，算出 `{run_id, status, outcome, halted_at}`。
租户隔离复用已有的 `_run_for_tenant`（判据只该有一份）。

#### 7. `src/views/tickets/useTickets.js` — 展示状态从 run 派生

| run 的情况 | 列表显示 |
|---|---|
| `outcome=halted` | **缺少必要信息** |
| `status=success` | resolved |
| `status=failed` / `cancelled` | failed |
| 还在跑 | running |
| 没发起过 run | 用后端工单自己的状态（new） |

`counts` 与 `visible` 一起改走展示状态 —— 只改 `visible` 的话，"中断"的工单会被
算进 In Progress，点进去却一条都没有。

#### 8. `TicketsView.vue` — 状态徽章、筛选 chip、新增 KPI 卡片（6 列）

---

## ⚠️ 一个要拍板的口径

`success → resolved` 是**约定**："诊断→修复→提交这条链走完了"。
它**不等于**"事故已确认解决"（那要看 PR 合没合、服务真恢复没有，本测试床没有那条
反馈回路）。要改口径只改 `RUN_TERMINAL_TO_TICKET` 那张表。

| 生产构建 | 通过 | `npm run build` ✓ | OK |
