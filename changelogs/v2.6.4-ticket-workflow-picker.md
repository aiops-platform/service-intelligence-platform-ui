# v2.6.4 — New Ticket 表单增加「执行流程」，建单时就把这张单钉到一条 workflow 上

**日期**: 2026-09-22

**需求**: 「在创建 ticket 的页面增加选择 workflow 的功能，并且能让 ticket 按照选定 workflow 执行」。

---

## 背景：手动建的工单此前**够不着**「钉住流程」这件事

后端今天（`8fe2101`）给 `POST /tickets/{tid}/run` 加了三层选流程的机制
（`_workflow_for_ticket`）：

```
① body 的 workflow_id（人工覆盖） > ② 工单钉的 workflow_name > ③ saved[0]（库里最新一条）
```

但 ② **只有 YAML 里的 `kind: ticket` 节点够得着**（`next_workflow` → `tickets.workflow_name`）：

- `TicketRequest` 没有 workflow 字段，`create_ticket` 也不传 `workflow_name`
  → 手建单的该列**永远是 NULL**
- 前端 `useTickets.js` 里没有任何 workflow 相关代码，`workflowApi` 都没 import

**实测（otr）**：29 张工单**全部未钉** → 全部走 ③ 兜底；而兜底是 `created_at` 最新那条，
推一条新流程就整体改道。用户在 Ticket Inbox 上**没有任何办法指定"这张单该跑哪条"**。

## 改动

### 后端（`multi-agent-workflow`）—— 只缺 2 处

列、`TicketStore.create(..., workflow_name=)`、`WorkflowStore.get_by_name`（重名取最新 +
告警）、运行期 409 —— **全都现成且有测试锁着**。本次只补：

1. `TicketRequest` 加 `workflow_id`。
2. `create_ticket` 把它**查回名字**再存进 `workflow_name` 列。

**「收 id、存名字」是刻意的，两个方向各有理由**：

- **收 id**：调用方（前端）手里只有 id，而 `workflows.name` **没有唯一约束** ——
  收名字的话重名时无法指定是哪一条，`get_by_name` 会静默取最新那条（与选中的可能不是同一个）。
- **存名字**：那是既有契约 —— YAML 跨租户同一份，而 id 每个租户库都不同，
  名字才是可移植的键；运行期 `_workflow_for_ticket` 正是按名字查回来的。
- **此刻就校验**：查不到 → **404，且在 `tickets.create` 之前**。否则会留下一张
  "钉了个不存在的流程"的废单，要等点「发起诊断」才 409 —— 那时单已经建出来了，
  而**界面上看不出它是一张废单**（钉住的列不显示在列表里）。

### 前端

1. `useTickets.js`：`draft.workflowId` + `workflow_id` 进 payload；新增
   `loadWorkflows()` / `workflows` / `fallbackWorkflowLabel`（照抄
   `useBugSolveRun.js` 那份既有写法的形状）。
2. `TicketsView.vue`：表单里加一个**整行**的下拉（选项文案是流程名，可能很长，
   塞进两列网格会被截断 —— 而这一格恰恰最不该靠猜）。
3. **详情抽屉加一行「执行流程」**：没有它，"我建单时选了哪条"在界面上**没有任何回执**，
   这套接线就是不可观测的。

### 空选项写明"不指定会跑哪条"

```
（不指定 —— 将跑：problem-diagnose-fix）
```

不是含糊的"不指定"。理由有两条：

- 不写清的话，「我没选」与「我不知道它会跑什么」在界面上长得一样；
- 而**兜底那条是会变的**（推一条新流程就换），所以这句话必须**当下算**——
  列表在**打开模态时**拉，不是在页面挂载时拉。挂载时拉的会是一份旧名单，
  标签指的那条**已经不是**真会跑的那条。

实现上 `workflows[0]` 就是兜底那条：`GET /workflows` 是 `created_at DESC`，
而未钉的工单取 `saved[0]` —— **同一个判据，不另算一套**（另算必然会漂）。

### 顺手拆掉一颗地雷

`startRun` 原先是 `ticketApi.run(ticket.id, ticket.workflowId)`。`workflowId` 是 camelCase，
而后端行里那个字段叫 `workflow_name` → **恒为 undefined**。今天无害（传 undefined 等于不传，
恰好让"钉的"生效），**但那是巧合不是设计**：一旦有人"顺手把它改对"（改成
`ticket.workflow_name`），传进去的会是**名字**，而 `run` 的 body 要的是 **id**
—— 要么 404，要么跑错一条。改成显式不传，并写明人工覆盖是另一个动作。

## 验证

### 后端

`pytest tests/test_tickets_api.py` **22 passed**（+4 条新用例）；全量 **538 passed**。

新增用例：钉住时**存的是名字**（并回读确认）、钉不存在的 id → **404 且一张单都不建**、
不传/空串/空白 → 一律不钉、以及**本功能的验收用例**——建单选了**旧的那条**
（兜底本来会跑新的）→ 发起诊断跑的就是选的那条。

**变异验证**（两次，各杀中目标）：① 改成存 id 不存名字 → 名字断言 + 验收用例红；
② 去掉建单时校验 → "不留废单"用例红。

**真环境（otr，零 LLM，探针按显式 id 清理，残留 0）**：

```
① POST /tickets {workflow_id}       → 201，直查库 workflow_name = 'problem-diagnose-fix'（名字，非 id）
② POST /tickets {workflow_id: 不存在} → 404，工单数不变（没建出废单）
③ POST /tickets（不传）             → 201，workflow_name = NULL
```

⚠️ **没有真起 run**（耗 token）：运行期解析由 pytest 的验收用例覆盖，不重复烧钱。

### 前端（CDP 对真实页面；本仓无前端测试框架）

- 下拉 4 项（1 空 + 3 条流程），**值与 `GET /workflows` 逐条一致**；
  空选项文案里那条 **= 后端返回的 `[0]`**（`labelMatchesBackendFirst: true`）。
- 选第 3 项（刻意不选第一条，否则"选了"与"没选"分不出来）→ 提交 →
  **拦 `fetch` 截获真实请求体**：`workflow_id = "93eed1138e7a"`，与选中项一致；
  （拦截后返回伪造 201，**不往库里建单**）。
- 详情抽屉两个分支：未钉 → `执行流程 未指定（跑库里最新一条）`；
  已钉（拦 `GET /tickets/{id}` 注入 `workflow_name`）→ `执行流程 problem-diagnose-fix`。
- `npm run build` 通过。

## ⚠️ 未验证 / 已知边界

- **PG 分支零测试覆盖**（全仓既有状况）：新逻辑走 `cs.ticket.create`，PG 实现在本仓
  同样没有用例跑到；本机租户库都是 PG，真环境那三条其实是**打到 PG 的**，
  算是一点补偿，但 SQLite 侧只有单测覆盖。

  改名会让已建工单在发起时 409（那是 h.a.hu 既有设计，本次不改）。
