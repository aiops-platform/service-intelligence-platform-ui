# v2.2.7 — Smart Inspection 两列改为「按服务的未解决问题数」并下钻 Problem Center

**日期**: 2026-09-18

**问题/背景**: 需求 ——

1. Alerts 列显示该服务**指标类问题**的未解决数量；
2. Log Anomalies 列显示该服务**日志类问题**的未解决数量；
3. 两列**都排除已解决**；
4. 点任一列的徽标 → 跳到 **Problem Center**，预筛选为「该服务 + 该类型 + 只看未解决」。

**根因**：两列此前实际都显示 `-`。Alerts 列读 agentflow `app-indicators` 的 `alertCount`，
线上三个服务**全是 `null`**；Log Anomalies 列在 v1.2.2 之后 `logErrorCount` 被硬编码成 `null`
（数据源下线）。而上一轮（v2.2.6）隐藏 metrics-analysis / log-analysis 后，徽标的点击落点也
成了死链（静默弹回 `/service-ops`）。

**核心不变式**：徽标上的数字 == 点进去 Problem Center 后看到的行数（`#pcRowCount`）。

---

## 改动明细

### 1. `js/app.js:45-133` — IIFE 顶层的共享谓词 + 取数（新增）

**原因**: 不变式只有在两侧用**同一套**判定时才成立。各写一份的话今天能对上纯属巧合，后端一改
就静默漂移。`initSmartInspection` 与 `initProblems` 是两个独立闭包（本文件单 IIFE 内每个
`initXxx()` 自成闭包），所以谓词必须放顶层共享。

新增：`problemIsOpen` / `problemHasMetric` / `problemHasLog` / `problemServiceNames` /
`problemMatchesService` / `problemMatchesType` / `fetchProblemRecords`。

判据要点：

- **未解决 = `state ∈ {pending, in_progress}`（白名单）**，与 Problem Center 自己的 "Open"
  chip 逐字相同。刻意不用「排除 resolved/closed/archived」的黑名单写法 —— 后端将来加状态时，
  白名单会让两侧*一样地*不计入，黑名单会一边算一边不算。
- **类型按证据存在与否**（`metric_anomalies` / `log_anomalies` 谁非空），**不**用后端的
  `detection_type` 等值判断 —— 它是 `log/metric/combined/unknown`，`combined` 记录在等值判断下
  两种筛选都匹配不上；按证据判断则两列各计一次，这正是它与 Problem Center 两个 chip 都能对上的原因。
- **service 按成员匹配**而非整串相等（后端的 `service` 可能是逗号拼接的多服务串）。

`fetchProblemRecords()` 的 base/tenant/key **在调用时**读 localStorage，不用顶层 `var` 缓存
（那会把值冻结在脚本加载那一刻）。三份既有的闭包内 `apmApi` 副本（`:3756/:6077/:6466` 附近）
原样未动。

### 2. `js/app.js:1409-1417, 1585-1665` — Smart Inspection 侧取数与汇总

- 闭包状态：`problemTally` / `problemsLoading` / `problemsTimer` / `problemsDiagLogged`。
  `problemTally === null` 表示**从未成功拉到**（渲染 `-`：不知道 ≠ 没有）。
- `buildProblemTally(items)` (`:1591`)：只计未解决；`combined` 两列各计一次；多服务合并记录
  在它点名的**每个**服务下各计一次。
- `fetchProblemTally()` (`:1619`)：**独立的 in-flight 标志**（不复用 `isLoading`，共用会让 5s
  轮询被整轮跳过）+ **独立的失败路径** —— 绝不碰 `siErrorBar` / `siLoadingOverlay` /
  `showError()`，只 `console.warn` 并保留上次计数。否则 APM 挂了会让整页看起来坏掉。
- `logProblemsDiagOnce(items)` (`:1644`)：跨后端 join 的一次性诊断（页面服务数 / 问题里的服务名
  / 没匹配上的名字）。服务名来自 agentflow、问题来自 APM，两套后端两套命名，一旦对不上症状是
  「两列全 0」，这条日志把它变成一眼可诊断。

### 3. `js/app.js:1725-1745` — 徽标标记与取值

`alertBadge(count, serviceName, kind)` 新增第三个参数 `kind`，并改写可点判据：

| count | 渲染 |
|---|---|
| `null` | `<span class="si-alert-badge null-alert">-</span>`，**不带任何属性** → 不可点 |
| `0` | 灰底 `0`，**带** `data-service` / `data-kind` → 可点（用户要求「点任意」） |
| `> 0` | 原 `has-alerts` 红底，同样带两个 data 属性 |

`data-service` 保留原有的 `.replace(/"/g,'&quot;')` 转义，**未**改用 `escapeHtml` —— 后者基于
`createTextNode`，转义 `& < >` 但**不转义引号**，放在属性位上会逸出。
新增 `problemCount(serviceName, kind)` (`:1738`) 供表格、KPI、抽屉三处共用。

### 4. `js/app.js:1755-1758` — `renderSITable` 两个单元格

```diff
- '<td>' + alertBadge(s.alertCount, s.name) + '</td>' +
- '<td>' + alertBadge(s.logErrorCount, s.name) + '</td>' +
+ '<td>' + alertBadge(problemCount(s.name, 'metric'), s.name, 'metric') + '</td>' +
+ '<td>' + alertBadge(problemCount(s.name, 'log'), s.name, 'log') + '</td>' +
```

### 5. `js/app.js:2348-2365` — 点击委托

选择器 `.si-alert-badge.has-alerts` → `.si-alert-badge[data-kind]`（0 的徽标也要能点），
**删掉**原先靠「行内最后一个 has-alerts 徽标」推断日志列的逻辑 —— 那个推断对 `combined`
记录本来就是错的。落点：

```js
navigateToPage('problems', { service: serviceName, type: kind, state: 'open' })
```

### 6. `js/app.js:1782-1798, 1855-1858` — Total Alerts KPI 与详情抽屉

原先分别读 `s.alertCount`（线上恒 `null`）→ KPI 恒 0、抽屉恒 `-`，改完两列后会出现
「表里写着 2、KPI 写着 0、点开抽屉写着 -」。两处一并改为读同一份计数；抽屉的
`Alert Count` 一行拆成 `Metric Problems` / `Log Problems` 两行，与表格两列一一对应。

### 7. `js/app.js:2430-2445, 2455` — 轮询

新增独立的 `problemsTimer`（**15s**），不挤进原有的 5s 服务轮询：`/v1/problems?limit=500`
响应很肥（单条记录带 `evidence` / `trace_ids`，实测约 4KB），每 5s 拉一次纯属浪费。两条定时器
同样按面板可见性 gate。首屏与手动刷新按钮（`:2385`）也各拉一次。

### 8. `js/app.js:4087-4110` — `loadServiceFilter` 补齐缺失的服务 option

原逻辑只在 `seen[currentService]` 为真时选中，于是从一个**零问题**的服务（徽标显示 `0`）
下钻过来时，`allProblems` 里没有它 → 下拉框回落显示 "All Services"，而表格其实正按该服务过滤
—— 控件在说谎。改为缺失时用 `createElement` + `textContent` 补一个 option 并无条件选中。

### 9. `js/app.js:3956-3961, 4134-4170, 4188-4205, 6325` — Problem Center 接收 URL 筛选

- `currentType` + `TYPE_FILTERS` / `STATE_FILTERS` 白名单（手敲的 URL 不该能把页面卡在一个
  没有任何 chip 能清掉的值上）。
- `applyQueryFilters(queryArg)`：有参才生效，否则完全不动（保持用户当前筛选）。参数化成可选
  入参，将来第二个 legacy 页面需要上下文时改走 `showPage(pageId, query)` 即可。
- `filteredProblems()`：服务那行换成 `problemMatchesService`（按成员），新增
  `problemMatchesType`，`open` 分支改用共享的 `problemIsOpen` —— 与徽标侧逐字同一口径。
- `_pageRefreshers['page-problems']` 改为先 `applyQueryFilters()` 再 `refresh()`（顺序不能反：
  `refresh` 内部的 `loadServiceFilter` 依赖已设好的 `currentService`）。

> **为什么读 `location.search` 而不是扩 `__SIP_SHOW_PAGE` 接缝**：`__SIP_NAVIGATE`
> （`src/router/index.js:198`）本来就把 context 转成 URL query，注释里也承诺了「可分享、可刷新、
> 可前进后退」，只是接收端从来没人兑现（`router.afterEach` 只递 `meta.panelId`，`showPage`
> 只收一个参数）。读 `location.search` 把这个已文档化的机制补完，改动全部落在本文件；改接缝
> 则要连 CLAUDE.md 里登记的签名、`showPage`、路由三处一起动。
> **不要**从 PC 的 chip 回写 URL（`history.replaceState` 会绕过 Vue Router 让 `currentRoute`
> 与地址栏失步），代码里已注释说明。

### 10. `src/legacy/legacy-panels.html:1023-1031` — Problem Center 加类型 chip 组

`All Types` / `Metric` / `Log`，**逐字复用**既有 `.filter-chip` / `.chip-dot`，未新增 CSS、
未动 `css/styles.css`。绑定在 `js/app.js:6146`，查询用 `legacyRoot().querySelectorAll(...)`
（CLAUDE.md 要求全文档查询收进 `legacyRoot()`；紧邻的两个 chip 组是裸
`document.querySelectorAll`，属既有写法，本次未顺手改以免铺开 diff）。

### 11. `js/app.js:2460-2490` — 修 `initFilterChips` 的作用域（**既有 bug**）

**这是一处顺带修掉的既有 bug，也是新 chip 能正常高亮的前提。**

原实现查的是 `legacyRoot().querySelectorAll('.filter-chip')`（**全文档**），于是每一个已经
在自己 `initXxx()` 里绑过 click 的 chip 组都被**追加了第二个** handler；而 `init()` 里
`initFilterChips()` 排在最后，所以它总在持有者**之后**执行 —— 持有者刚 `add('active')`，
它立刻 `toggle` 掉。症状：**Problem Center 的 severity/state chip 点完根本不亮**。
「All」分支更糟：它会清掉全文档所有 `.filter-chip` 的 `active`，包括别的面板的组。

改为只作用于 `#page-service-ops .filter-chip` —— 那 12 个裸 chip
（`legacy-panels.html:106-118`）是**唯一**没有自己绑定的组。

### 12. `src/router/nav.js:130-141` — 更新已失效的注释

v2.2.6 留下的注释说「徽标会静默落进 catch-all 回到 /service-ops」。该入口已于本次改道到
Problem Center，注释改为指向新落点，并保留摘叶子的说明。

> 踩坑记录：注释里写 `**/problems**` 会让 `**/` **提前终止块注释**，导致 nav.js 整个文件
> 语法错误、`npm run build` 直接失败（报错位置还在几十行之后，颇具迷惑性）。
> 已改写为不带 `*/` 的措辞。本文件是 ESM，`node --check` 也查得出来。
