# v2.6.6 — Diagnosis Center 的「Escalate」：一键把问题单派给修复流程（建单即钉 `bug-fix-scenario2`）

**日期**: 2026-09-22

**需求**: 「我想在 Diagnosis Center 页面中，再增加一个按钮 escalate，当我点击这个按钮的时候，他就直接请求
ticket 的接口，生成 ticket，然后默认使用 workflow name 为 `bug-fix-scenario2` 这个进行后续的分析。」
外加显示规则（需求方当场确认）：**列表行**只在**还没分析过**的单上出现；**弹框**只在**分析过但没根因或没方案**
时出现（也就是今天弹框里只剩「忽略」的那两种情况）。弹框文案「升级 · 修复流程」，列表行英文 `Escalate`。

---

## 背景一：为什么"直接请求 ticket 的接口"要**经 APM 转一手**

字面做法是浏览器直接 `POST /agentflow/tickets` 并带上 `workflow_id`。三条事实让它不成立：

1. **工单号只有 APM 会生成**（`INC-YYYYMMDD-NNNN`，`SequenceStore.next_ticket_number`）。agentflow 的
   `tickets.number` 是"外部工单号"的自由文本列，平台不生成 —— 绕过去建的单是**没有号**的。
2. **问题单与工单的绑定写在 APM 的 evidence 里**（`find_by_ticket` 按号反查就靠它）。
3. 于是那张单修完之后，`ticket-done` 节点回传（`POST /v1/problems/ticket-status`）**反查不到记录**（404），
   v2.6.5 刚接好的「处理 · DECISION 显示处置结论」对这些单永远不会亮，列表的 Ticket 列也永远是 `-`。

所以新增一个 APM 端点：它取号、建单（把流程钉上）、写绑定、转终态 —— 前端仍然只是"点一下"。

## 背景二：这条不经过诊断裁定

现有的「升级 · 生成工单」要有一轮诊断、要放行 agentflow 的审批门，工单由 run 里的 `kind: ticket` 节点按
YAML 的 `next_workflow`（`problem-diagnose-fix`）建出。**没诊断过 / 诊断没给出方案的单根本走不了那条路**
（前者没有 run，后者没有可派的方案）—— 这正是一个**直接派单**入口要解决的问题。两者产出的 evidence
形状刻意保持一致（见改动 1 的说明）。

---

## 改动明细

### 1. `aiops-apm-anomaly-detector/src/aiops_apm/router/problems.py` — 新端点 `POST /v1/problems/{record_id}/escalate`

```python
class EscalateBody(BaseModel):
    workflow_name: str = ""      # 传名字不传 id：id 每个租户库都不同，名字才是可移植的键
```

流程：取号 → 按名字查回 workflow id → `POST {agentflow}/tickets`（带 `workflow_id`）→ 写 evidence →
`mark_escalated`。三道守卫：

| 守卫 | 结果 | 为什么 |
|---|---|---|
| 已持有工单（`_created_ticket`） | 409 `already holds ticket <号>` | 幂等；放在终态守卫**之前**，因为"是哪个号"比"is escalated"有用得多 |
| 已是终态（`_TERMINAL_STATES`） | 409 `escalate not allowed` | resolved/closed 的单不能替现场翻案 |
| 名字查不到 | 404（**在建单之前**） | 钉 A 却跑 B 比跑不起来危险（与 agentflow `_workflow_for_ticket` 的 409 同一个理由） |

**evidence 与「升级裁定」同一个形状**（`{type:"diagnose_decision", decision:"escalate", ticket_id, ticket_number}`），
只多两处：`engine: "manual"`（人直接派的）与 `workflow_name`；**不写 `session_id`** —— 它没有诊断轮次。

> 这个形状不是我选的，是仓里既有的纪律：`_created_ticket` 的 docstring 写得很清楚 ——
> 「升级」与「它建出的那张工单」是**同一件事**，拆成两条 evidence 会让读的人自己拼、还多一个只写不读的类型。
> 顺带白拿三处复用：后端 `_holds_ticket` 反查、前端 `problemTicketNumber` 的号、历史计划的「已升级」chip。

### 2. `problems.py:1275` — `_resolve_workflow_id()`：名字 → id

`workflows.name` **没有唯一约束** → 重名取 `created_at` 最新那条，与 agentflow `get_by_name` **同一口径**
（否则"建单时钉的"与"发起时跑起来的"可能不是同一条，而两边都不会报错）。

### 3. `problems.py:1299` — `_agentflow_create_ticket(..., *, workflow_id="")`

原函数只服务 spike 老路径且不钉流程；加一个可选参数，非空才写进 payload（agentflow 收 id、存**名字**）。

### 4. `diagnosis/from_agentflow.py:105` — `fetch_workflows()`

**失败返回 `None` 而不是空表**（与 `fetch_traces` 那类"失败回空表"刻意不同）：调用方要按名字解析 id，
把"上游挂了"当成"库里没有这条流程"，就是把**部署故障报成配置错误** —— 人照着那句话去查名字/改 YAML，白跑一趟。

### 5. `tests/test_problem_escalate_api.py`（新，7 条）

钉流程 / 不钉就不查流程表 / 幂等 409 且不再出站 / 未知流程 404 且不建单 / 上游挂 502（不是 404）/
终态 409 / **闭环：直接派单写下的号，回传反查得到这条记录**。

### 6. `js/app.js:4378` — 列表行的 `Escalate`

```js
((st === 'pending' || st === 'in_progress') && !diag ? '<button ... data-act="escalate-fix">Escalate</button>' : '')
```

与 `Analyze` 并列（两个都是"现在就动这条单"：一个让平台诊断、一个直接派给修复流程），`Ignore` 仍在其后。
判据与 `View diagnosis` 互补 —— 有诊断的行不出现它。

### 7. `js/app.js:5054` — 弹框的「升级 · 修复流程」

```js
var rootCause = String((snap.conclusion && snap.conclusion.root_cause) || '').trim();
var canEscalateFix = (!rootCause || opts.length === 0);
```

与 `canEscalate`（现有「升级 · 生成工单」）**并列而非互斥**：两者只在"有方案但没根因"时同时出现，那时派的
确实是两件事。hint 同步改口：`本次诊断未给出可执行方案，仅可忽略。` → `…可忽略或升级到修复流程。`
（那句旧文案与按钮逐字成对，不改就是在说反话）。

### 8. `js/app.js:5110` — `escalateToFix(rec, modal)`：两处共用一个动作

调 `POST /v1/problems/{id}/escalate {workflow_name: 'bug-fix-scenario2'}`（常量 `ESCALATE_FIX_WORKFLOW`）。
成功后：弹框那条就地翻 `pcDiagRec.state` + 落 `dgxTicket`（复用 v2.6.5 的工单卡），列表那条只 `refresh()`。
两处都有二次确认（会真的建单，与「忽略」同款）。toast 语言随各处既有习惯（列表英文、弹框中文）。

### 9. `js/app.js:5474` — 历史计划里那句「该轮快照不可用」

直接派单那条**没有** `session_id`，原先会无条件印出「该轮快照不可用（诊断会话已过期）。」——
它压根没有会话，这句话是把不存在的东西说成过期了。改成 `if (it.session_id)` 才印。有诊断轮次的条目
（spike/agentflow 裁定）行为**逐字不变**。

### 10. `css/styles.css:4998` — `.pc-escalate-btn`

与 `.pc-diag-btn` / `.pc-viewdiag-btn` 同一支紫（`.dgx-btn--escalate` 也是这支），写在它们**之后**
（同权重后写的赢，本表是"到处追加"的长文件）。

## 踩坑记录：本地 `ticket_seq` 计数器是停的 → 实测第一单就撞了重号

第一次实测，新记录拿到的号是 `INC-20260922-0001` —— 而当天上午这两张单已经用过 `0001`/`0002`
（`68f3c580161f` / `59cb5f0d3965`）。查 `aiops_apm_runtime.ticket_seq` 才看清：`20260922` 那一行
`next_seq = 1`，也就是说**计数器里没有那两号的记录**（应是早先存储后端切换时这张表被重建过）。

后果不只是"号重复"：`find_by_ticket` 按号反查，两个记录都自称持有 `INC-20260922-0001` → 回传可能翻错单。
已把该行 `next_seq` 修到 2（这一次实测又用掉 0003 → 现为 3）。**生产没有这个问题**（计数器单调），
但本地再测回传链路前值得先看一眼这张表。

## 未处理

   下一步是把它做成工单表单那样的选择器（Vue 侧 v2.6.4 已有 `workflowApi.list()` 可抄）。
2. **`closed_manual`（驳回达上限）且仍有方案的诊断**：按需求方定的规则，两处 Escalate 都不出 ——
   那种单今天仍然只能「忽略」。要给它留出路的话，判据里加 `st === 'closed_manual'` 即可。
3. **派单后不会自动跑**（需求方选的「只建单，钉住流程」）：工单躺在 Ticket Inbox 里等人点「发起诊断」。
   要"点一下跑到底"就把 `POST /tickets/{tid}/run` 接在派单成功之后。
4. **实测用掉的号段留了一个空洞**（`INC-20260922-0003` 随测试工单删除）。本仓对号段空洞是接受的
   （`sequence.py` 明说"两边都有空洞"），没有回填。
