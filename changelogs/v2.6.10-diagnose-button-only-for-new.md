# v2.6.10 — 列表里「发起诊断」只给「新建」的工单

**日期**: 2026-09-22

**需求**: 「只有新建状态列表才显示发起诊断按钮」。

---

## 改了什么

操作列此前**无条件**渲染「发起诊断」—— 33 行 33 个一模一样的黄色按钮。

```html
<button v-if="ticketDisplayStatus(t) === NEW" ... >发起诊断</button>
<span v-else style="color: var(--text-tertiary)">—</span>
```

新增展示态常量 `NEW = 'new'`（`useTickets.js`），与既有的 `NEEDS_INFO` /
`WAITING_APPROVAL` / `PAUSED` / `REJECTED` 并列，**不写魔法字符串**。

## 判据：为什么是 `new`，以及为什么用**展示状态**而不是 `t.status`

`new` ⟺ **一次 run 都没跑过**：后端一发起 run 就把它置成 `running`
（`run_ticket` 的 `set_status`），之后不再回写。

⚠️ 这里 `ticketDisplayStatus(t) === NEW` 与 `t.status === 'new'` **恰好等价**，
但选前者是因为它是**同一份判据** —— 展示状态还管着 halted / 审批否决那些派生档，
以后再加派生档时，用 `t.status` 判会悄悄跑偏（而那正好是 `ticketDisplayStatus` 存在的理由）。

## 为什么该藏起来（不只是"按需求做"）

那一列全是同样的按钮，**信息量为零**；而跑过的单在 Run 列已经能点进去看。
更实际的是它会误导：33 行都有按钮，看起来像"每一条都还没跑过"。

**重跑走详情里的「再跑一次」**（`rerunFromDetail`，本次未动）—— 那是"看过现状之后"的动作；
摆在列表里等于鼓励人盲点。

## 验证（CDP 对真实页面；本仓无前端测试框架）

逐行统计「状态 ↔ 有没有按钮」：

| 状态 | 行数 | 有按钮 |
|---|---|---|
| **新建** | 2 | **2** |
| 已解决 | 7 | 0 |
| 失败 | 5 | 0 |
| 已暂停 | 1 | 0 |
| 审批超时 | 10 | 0 |
| 缺少必要信息 | 6 | 0 |
| 审批不通过 | 2 | 0 |
| **合计** | **33** | **2** |

33 行里**只有那 2 条「新建」有按钮**，其余全部显示 `—`。
截图人工确认：`INC0001021`（新建）是全表唯一带「发起诊断」的行。

`npm run build` 通过。
