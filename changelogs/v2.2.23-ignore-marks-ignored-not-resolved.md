# v2.2.23 — Diagnosis Center 的 Ignore 不再写成 resolved：状态变 ignored，且不再被记成误报

**日期**: 2026-09-21

**问题/背景**: 用户指出「在 Diagnosis Center 这个页面中，当我点击 Ignore 的时候，提交后，
我的数据状态应该变成已忽略对应的英文吧，而不是 resolved，对不，因为我也不需要解决它，
我是点击的忽略的」。

查证属实，而且比"文案不对"更严重 —— 同一个请求还顺手把这条单记成了一次**误报**。

---

## 根因

表格行上的 `Ignore` 按钮打的是**「已解决」的端点**（`js/app.js:4482`，改前）：

```js
apmApi('/v1/problems/' + id + '/resolve',
       { method: 'POST', body: { false_positive: true } })
```

后端 `/resolve` 无条件写 `state='resolved'`（`aiops-apm-anomaly-detector/src/aiops_apm/router/problems.py:178`），
两个后果都是错的：

1. **状态列显示 resolved** —— 用户点的是「忽略」，库里却记「已修复/已处理」，
   界面照实回显 resolved，等于替用户编造结论。
2. **顺带记一次误报** —— `false_positive: true` 触发 `_record_fpr()`：写 `fpr_table`
   （total+1、重算 fpr）并刷新 `aiops_false_positive_rate` Gauge。
   忽略 ≠ 误报：忽略是「先搁置不看」，误报是「这次检测报错了」，后者是 L3 误报率闸门的输入。
   每点一次忽略就污染一次误报率。

页面自己的提示文案当时也是这么写的（`legacy-panels.html:1059`）：
`Analyze for detail · Ignore marks as false positive`。

### 后端其实已经分好了两个终态，只有这个按钮用错了

| 终态 | 语义 | 入口 |
|---|---|---|
| `resolved`（+reason auto/manual/false_positive） | 已修复/已处理 | `records.resolve()` |
| `closed`（+reason ignored） | 人判定不做（忽略） | `records.close()` |

诊断弹框里的「忽略」走 `POST /{id}/diagnose/decision {ignore}` → `records.close(reason="ignored")`，
**不记误报 —— 弹框一直是对的**。同一个页面里两个「忽略」语义不同，是这次暴露出来的不一致。

## 改动明细

### 1. 后端（另一仓库）`router/problems.py:190` — 新增 `POST /v1/problems/{id}/ignore`

与 `/resolve` 对称的入口，走 `records.close(reason="ignored")`，返回 `{"state": "closed"}`。

**为什么不能让前端直接复用 `/diagnose/decision`**：那条路径要求该单**绑过诊断**
（没绑 → 409 `no diagnosis bound`），而行上的 Ignore 对**所有** pending/in_progress 行都在显示，
包括从没 Analyze 过的；且它会往 evidence 写一条 `diagnose_decision`，让这行在弹框的
「历史计划 · PLAN HISTORY」里当成一个方案版本冒出来。所以补一个轻量端点。

新端点**刻意不碰诊断会话**（`/dismiss` 收尾仍归 `/diagnose/decision`），原因同上：
它要对没绑过诊断的单同样可用。这一点写进了 docstring，免得以后被"合并成都是关单"。

`/resolve` 的 docstring 也补了一句指向 `/ignore`，避免再被误用。

### 2. `js/app.js:70` — 新增共用的展示状态 `problemDisplayStatus(rec)`

```js
function problemDisplayStatus(rec) {
    var st = String((rec && rec.state) || 'pending').toLowerCase();
    var reason = String((rec && rec.resolve_reason) || '').toLowerCase();
    if (st === 'closed' && reason === 'ignored') return { cls: 'ignored', label: 'ignored' };
    return { cls: st, label: (rec && rec.state) ? rec.state : 'pending' };   // 其余原样
}
```

判据**只写一份**（表格列 `js/app.js:4281` 与详情模态 `js/app.js:4366` 共用）——
各写一份就会出现「列里写 ignored、弹框里写 closed」。

- `cls`：`styles.css:2168` 的 `.alert-tag.status-ignored`（灰色）**本来就有**，
  与原先 `closed` 用的 `.status-closed` 同色，**无需改样式表**。
- 兜底分支**原样返回 state**（含大小写），非忽略的行与改前**逐字一致**。
- 只认 `closed + reason=ignored`：后端 `close()` 目前只有 `ignored` 这一个调用点，
  但按 reason 判，将来多一个关闭原因时不会跟着一起说成「忽略」。

### 3. `js/app.js:4482` — `confirmIgnore` 改打 `/ignore`

去掉了 `body: { false_positive: true }`；确认文案同步改成
`Ignore problem PR-xxx? It will be marked as ignored.`（原文案还在宣传错误行为）。

**文案先写成 `It will be closed as ignored (not a false positive).`，被用户打回**
（「not a false positive 这是啥意思，我没懂」）。错在：点忽略的人脑子里没有「误报」这个概念，
括号里的对比是写给**读过旧文案的人**的，对其他人就是读不懂的噪音；而弹框只需要说
"点下去会发生什么"。误报要解释就留在误报自己的入口上。

### 4. `src/legacy/legacy-panels.html:1059` — 页脚提示文案

`Ignore marks as false positive` → `Ignore marks the problem as ignored`。
（同一条提示里也一度带了「要标误报请去诊断弹框」，一并去掉 —— 同一个理由。）

## 未处理

- **筛选 chip 仍叫 `Closed`**（筛选值 `?state=closed` 也不动）。于是忽略的单在「Closed」
  chip 下显示的却是 `ignored`。本次按用户「其他的逻辑暂时不变」的要求没动 chip 文案，
  要统一的话是 `legacy-panels.html:1022` 一行。
- **KPI 的 `Resolved` 不再把忽略的单算进去**（它本来就只数 `state === 'resolved'`）——
  这是修好之后自然的结果，不是额外改动。
- **历史误报数据不清理**：库里已有的 `fpr_table` 行（如 `default` 租户 gateway-service
  1/1、order-service 2/2，误报率 100%）很可能是历史上点 Ignore 留下的，本次只保证不再新增。
- `POST /ignore` 与 `/resolve` 一样**不校验当前状态**（幂等由 SQL 的 `state <> 'closed'` 兜底），
  按钮本身也只在 pending/in_progress 行显示。
