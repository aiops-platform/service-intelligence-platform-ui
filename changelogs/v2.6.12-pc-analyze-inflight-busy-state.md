# v2.6.12 — Diagnosis Center：Analyze 在途时按钮变「Analyzing」不可点，重复点击不再起第二个 run

**日期**: 2026-09-23

> 本文行号指**本次改动后**的当前文件。

**问题**: 列表行点 `Analyze` 之后、接口返回之前，按钮**看起来还是可点的 Analyze**，
点了也没有任何反馈。两个后果：

1. 用户无从判断第一次点击到底生效没有（于是自然会去重复点）；
2. **更糟的是重复点真的会起第二个 run** —— 见下面「踩坑 2」，这不只是观感问题。

---

## 改动明细

### 1. `js/app.js:4371, 4384-4390` — 按钮两种形态，忙碌态**从状态渲染**

**原因**: 表格每 5s 被轮询整体重建 `tbody.innerHTML`。点完直接改 DOM 的 `disabled` / 文案，
会被下一次 `renderTable()` 抹掉，而 `diagBusy` 还在——按钮就变成「看着能点、点了没反应」。
所以忙碌态必须和别的列一样**由数据渲染出来**。

```js
var diag = findAgentRun(p) || findDiagnoseSession(p);
+ var analyzing = !!diagBusy[p.record_id];
```

```js
-((st === 'pending' || st === 'in_progress') && !diag
-  ? '<button ... data-act="diagnose">Analyze</button>' : '') +
+((st === 'pending' || st === 'in_progress') && !diag
+  ? (analyzing
+    ? '<button class="btn-alert-detail pc-diag-btn" disabled>Analyzing</button>'
+    : '<button ... data-act="diagnose">Analyze</button>')
+  : '') +
```

### 2. `js/app.js:4654-4686` — `startDiagnose()`：点完立刻重渲染；成功**不再解除**忙碌态

**原因**: 解除的时机原本挂在 **POST 的返回**上，这是错的——POST 成功只代表「run 起来了」，
列表里的 `evidence` 还要等 `refresh()` 读回来。那之前 `diag` 仍为空，按钮若已恢复成
Analyze，再点一次就**真的起第二个 run**（`/analyze` 带 `rerun: true`，后端不拦）。

```js
 function startDiagnose(rec) {
     if (!rec || diagBusy[rec.record_id]) return;
     diagBusy[rec.record_id] = true;
+    renderTable();              // 立刻换成「Analyzing」（disabled）
     ...
     .then(function (data) {
-        delete diagBusy[recordId];          // ← 删掉：此刻列表还没回读
         var rid = ...
         refresh();
     })
     .catch(function (err) {
         delete diagBusy[recordId];          // 失败是终局，当场放回可点
         window._showToast('Analyze failed: ...', 'error');
+        renderTable();
     });
 }
```

### 3. `js/app.js:4691-4699` — 新增 `clearSettledDiagBusy()`

**原因**: 忙碌态改由**数据**解除——列表里这条已经能看到 `agent_run` / `diagnose_session`
就清掉。真源永远是列表那一份；`refresh()` 失败也不用特殊照顾，5s 的静默轮询会把数据带回来。

```js
function clearSettledDiagBusy() {
    for (var i = 0; i < allProblems.length; i++) {
        var p = allProblems[i];
        if (diagBusy[p.record_id] && (findAgentRun(p) || findDiagnoseSession(p))) {
            delete diagBusy[p.record_id];
        }
    }
}
```

在 `renderTable()` 开头（`js/app.js:4342`）调用一次，所以下面读 `diagBusy` 时
「为真 ⟺ 还没有 diag」这条不变式成立。

### 4. `css/styles.css:5007-5017` — `.pc-diag-btn:disabled` 样式（**请回** v2.2.9 删掉的那条）

**原因**: v2.2.9 把「已发起 → 置灰」改成「已发起 → 不渲染」，于是 `:disabled` 成了死样式被删。
本次它重新有了命中场景（**在途**，而不是「已发起」），所以请回来——但形态不同：不是灰底，
而是沿用弹窗里 `.dgx-btn:disabled` 的 `opacity: .45`。

```css
.pc-diag-btn:disabled,
.pc-diag-btn:disabled:hover {
    color: var(--accent-purple);
    background: #fff;
    border-color: var(--border-color);
    opacity: 0.45;
    cursor: not-allowed;
}
```

`:hover` 必须一起写：上面那条 `.pc-diag-btn:hover`（`:5006`）**不以 `:disabled` 为条件**，
光标扫过禁用按钮仍会把它染成「可点」的样子。两条同权重，靠写在后面才压得住。

### 5. 文案：「Analyzing…」→「Analyzing」（去省略号）

**量出来的，不是口味问题**。按钮 `min-width: 64px`、文字区约 46px：

| 文案 | 实测盒宽 | 该列被撑宽 | 左边各列的横向位移 |
|------|---------|-----------|------------------|
| `Analyze` | 64.0 | — | — |
| `Analyzing…` | 76.7 | +12.7 | 0 ~ **-12px** |
| `Analyzing` | 65.7 | +1.7 | 0 ~ -2px |

表格是 `table-layout: auto`，某一格内容变宽会让**整个操作列**变宽，代价是它左边所有列
（service / ticket / severity / state / time）横移——点一下整行抖一下。去掉省略号后
65.7px 落在 `min-width` 的那点余量里，位移 ≤2px。

## 踩坑记录

1. **忙碌态不能靠「改 DOM」**。这个页面的表格每 5s 被轮询重建一次 `innerHTML`，
   任何点完手动加上的属性都是**最长 5s 的临时状态**。凡是要跨渲染存活的状态，
   必须进 `renderTable()` 的渲染输入。
2. **原来的「防双击」只挡住了 POST 在途的那一段，挡不住它后面那一段**。
   `diagBusy` 是在 `.then` 里 `delete` 的，而 `refresh()` 没有 await——从 POST 返回到
   列表带上 evidence 之间有一整个窗口，此时按钮已恢复成可点的 Analyze，`diagBusy` 也为空。
   点下去 = 第二个 `/analyze`（`rerun: true`，后端不拦）= 真的起第二个 run。
   **「POST 成功」不等于「这件事完成了」**：这次的判据统一改成「列表数据里已经能看到结果」。
3. **失败路径必须自己重渲染**。忙碌态改由数据解除之后，失败时请求已经结束、数据却不会变，
   不手动 `renderTable()` 的话按钮会停在「Analyzing」直到下一次轮询（最长 5s）。
4. **按钮文案改动要先量宽度**，别凭感觉。这次差点为了一个省略号让整行在点下去的瞬间横移 12px。
   测量方法：克隆真实按钮节点、`textContent` 换成候选词、读 `getBoundingClientRect().width`。

## 影响范围

用 CDP 驱动真实 Chrome + 真实 APM 数据（`localhost:7070`）实测，`analyze` 请求在 CDP 层拦下
（hold / fail / fulfill），**全程没有真的起 run，数据零污染**。12/12 通过：

| 场景 | 预期 | 实际 | 状态 |
|------|------|------|------|
| 初始（pending / 无 agent_run） | 可点的 `Analyze` | `Analyze`，disabled=false，opacity=1 | OK |
| 点击后、接口未返回 | 变 `Analyzing` 且不可点 | text=`Analyzing`，disabled=true，opacity=0.45，cursor=not-allowed | OK |
| 在途连点 3 次（真实鼠标事件） | 不发第二个请求 | analyze POST 数 = **1** | OK |
| 请求失败 | 当场回到可点的 `Analyze` | `Analyze`，disabled=false，opacity=1 + 失败 toast | OK |
| POST 已返回、run 尚未回读 | **仍** `Analyzing`（旧实现此刻已放回 Analyze） | 仍 `Analyzing`，disabled=true | OK |
| 列表已回来但里面没有 run | 仍 `Analyzing` | 仍 `Analyzing` | OK |
| 列表带回 agent_run | 变 `View diagnosis` | Actions = `Detail, View diagnosis, Ignore` | OK |
| 全程请求数 | 2（两次点击） | 2（若防重失效则是 8） | OK |
| 布局稳定性 | 旁边各列不被挤动 | 表头/单元格位移 ≤2px，行宽不变 | OK |
| `node --check js/app.js` | 通过 | 通过 | OK |

**改动边界**：`Escalate` / `Ignore` **有意不动**——诊断在途时想「不等了，直接派单」是
一个正当选择，把它们一起禁用等于堵住用户的退路。（并发派单与诊断互相干扰是另一个独立问题，
本次不碰。）
