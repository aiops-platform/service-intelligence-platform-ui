# v2.2.21 — 审批超时/驳回不再显示成 resolved；修 `rejected-canceled` 节点回落成灰色

**日期**: 2026-09-21

**问题/背景**: 用户指出「超时后，流程不能显示 resolved，不合理。默认作为审批不通过处理，
并且标明不通过的理由是审批超时。」

查证属实，而且影响面比预想大：**列表里 11 条 "Resolved" 有 9 条其实是被否决或超时的。**

---

## 根因（后端，两处叠加）

审批超时时，sweeper 做的是（`approval/sweeper.py:95-105`）：

```python
await store.update_node_status(run_id, node_id, REJECTED_CANCELED,
                               output={"approved": False, "reason": "timeout"})
await self.queue.publish(..., {"type": "resume", ...})   # ← 发 resume 让下游照常收敛
```

于是：**「默认作为审批不通过处理」这一段本来就是对的**（`approved: false`，
且 `REJECTED_CANCELED` 在有向图求值时视同 REJECTED）。漏的是**对外表达**：

- `run.status` 只看"有没有节点失败"。超时到达的节点是 `rejected-canceled`
  （终态、非失败），其余节点照常收敛 → `status=done` → API `success`。
- 前端再把 `success` 映射成 `resolved`。

实测 `run_d8f3a5c560`：`approve-plan` 是 `rejected-canceled` / `reason=timeout`，
run 报 **success**，工单显示 **resolved** —— **方案审批被超时自动否决了，
却显示成"事故已解决"。**

---

## 改动明细

### 1. 后端 `api/app.py` — 新增 `_rejected_node()` / `_run_outcome()`

```python
def _rejected_node(nodes_raw) -> tuple[str, str] | None:
    """→ (node_id, reason)，reason ∈ {"timeout", "manual"}"""
```

理由优先读节点输出的 `reason`（sweeper 写的 `"timeout"`），读不到按状态兜底：
`rejected-canceled` → timeout，`rejected` → manual。

`_run_outcome()` 把三个字段打包，**三个消费面共用**（`GET /runs`、`GET /runs/{id}`、
工单的 `latest_run`）：

```python
{"outcome": "halted" | "rejected" | "completed",
 "halted_at": ..., "rejected_at": ..., "reject_reason": "timeout" | "manual" | None}
```

**为什么 `timeout` 与 `manual` 要分开**：状态上都是"没通过"，但读的人需要知道
**有没有人拍过板** —— "没人来处理"和"有人明确否了"是两个完全不同的后续动作。

**与 `_halted_node` 的关系**：两者在当前两条流程里**互斥** —— halt 的触发点
（scope / rca / locate）全在 `approve-plan` **之前**，一旦 halt，下游审批节点全部
SKIPPED，不可能再被否决。所以优先级顺序不影响结果，仍按 halted → rejected 排。

### 2. `src/utils/runStatus.js` — `REJECTED` 一档 + 补一条漏掉的节点映射

```js
export function runStatusOf(run) {
  if (isHalted(run)) return HALTED
  if (isRejected(run)) return REJECTED
  return run.status || ''
}
export function rejectReasonOf(run) { ... }   // timeout | manual | null
```

**并且补上一个真正的显示错误**：

```js
// ⚠️ 这条原先漏了，后果不是"少个颜色"而是**说反话**
'rejected-canceled': 'bs-node-status-rejected',
```

`rejected-canceled` 不在 `NODE_STATUS_CLASS` 里 → 落到兜底 `bs-node-status-pending`
—— 一个**被超时否决的审批节点在图上渲染成灰色"还没跑"**。
因为"审批超时"是本次才认真看的状态，一直没暴露。

### 3. `useTickets.js` — `rejected` 展示状态 + 按理由给文案

```js
if (r.outcome === REJECTED && r.rejected_at) return REJECTED   // 必须排在下面之前
...
return RUN_TERMINAL_TO_TICKET[r.status] || ''                  // success → resolved
```

`ticketStatusLabel(t)` 的入参**从状态字符串改成工单** —— 因为文案要看理由：
`timeout` → **审批超时**，否则 → **审批不通过**。

### 4. `TicketsView.vue` — KPI 卡片（7 列 → 8 列）+ 筛选 chip「审批不通过」

### 5. `css/styles.css` — `.alert-tag.status-rejected` / `.status-rejected-canceled`（红）

**红而不是琥珀**：琥珀在本仓表示"缺东西"（`halted` / `needs_info` / `waiting_approval`），
而这个是"**被否了**"，是另一回事。
