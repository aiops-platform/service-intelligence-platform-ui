# v2.0.0 — Service Ops 底部热力图去掉红色档（改「几乎全绿 + 1~2 个黄」）

**日期**: 2026-09-16

**需求背景**: Service Ops 页面最下方那张 `DAILY INCIDENT VOLUME · LAST 30 DAYS` 热力图，
30 个色块里现在有 9 个是暖色（2 深红 + 2 深黄 + 5 黄），整行看上去很"不健康"。
要求改成**几乎全绿、只留一两个黄的、不要红**。

---

## 结论先说：只能改阈值，不能改数据

`Heatmap` 组件（定义在 `public/_next/static/chunks/100pim9o6kpoy.js`）把 30 个值
**按本序列自己的 min-max 归一化**再分档上色：

```js
let c = Math.min(...e), l = Math.max(...e) - c || 1
… let o = (e - c) / l        // 每格的相对位置：0 = 本序列最小值，1 = 最大值
```

所以**最大值那一格恒等于 1.0，永远落在最高档**。原配色最高两档是红色，
于是无论怎么调数据，那一格都是红的。

> 唯一的例外是 30 个值**全部相等**：此时 `l = 0 || 1`，所有 `o = 0` → 全绿，
> 但那也就一个黄都没有了，不满足需求。

**要达到「几乎全绿 + 1~2 黄 + 零红」，只能改分档阈值。**

---

## 改动明细

### 1. `tools/tenant_copy.py` — 新增 `patch_heatmap_palette()` (line 316-380)

沿用本文件既有的构建期 chunk 补丁模式（与 `patch_ask_sip` / `patch_journey_slots` 同构：
**幂等**（已打过直接返回）、**不唯一就静默跳过**（站点改版不会把页面搞坏））。

```python
HM_FIND = ('background:o<.3?"rgba(16,185,129,0.40)"'
           ':o<.5?"rgba(16,185,129,0.65)"'
           ':o<.7?"rgba(245,158,11,0.55)"'
           ':o<.85?"rgba(245,158,11,0.85)"'
           ':o<.95?"rgba(244,63,94,0.85)"'
           ':"rgba(244,63,94,0.95)"')
HM_REPL = ('background:o<.5?"rgba(16,185,129,0.40)"'
           ':o<.9?"rgba(16,185,129,0.65)"'
           ':o<.95?"rgba(245,158,11,0.55)"'
           ':"rgba(245,158,11,0.85)"')
```

分档对照：

| `o` 区间 | 改前 | 改后 |
|---|---|---|
| `< 0.3` / `< 0.5` | 绿（浅） | 绿（浅） |
| `< 0.5` / `< 0.9` | 绿（深） | 绿（深） |
| `< 0.7` / `< 0.95` | 黄 | 黄 |
| `< 0.85` | 黄（深） | **黄（深）** ← 原为红 |
| `< 0.95` | 红 | **—（并入上一档）** |
| `≥ 0.95` | 红（深） | **—（并入上一档）** |

**阈值 0.9 是配合当前数据选的**：实测那 30 个值的 `o` 里只有 2 个 ≥ 0.9（1.000 与 0.970），
于是正好 2 格黄、28 格绿、0 格红。

> ⚠️ 这是**相对**刻度，换租户后数据分布变了，黄的格数会在 1~3 之间浮动 ——
> 但**最大值那格恒为黄**（`o` 恒等于 1），所以**永远不会再出现红色**。

### 2. `tools/make-offline-page.py` — 接进构建流程 (line 327-329)

放在既有一串 `patch_*` 之间（都在那个 `try/except` 里，失败只警告不中断构建）：

```python
+ if tenant_copy.patch_heatmap_palette(chunks_dir):
+     print("  热力图配色：三档（绿/黄/红）→ 两档（绿/黄），去掉红色")
```

### 3. `public/_next/static/chunks/100pim9o6kpoy.js` — 构建产物随之更新

这个文件是**已入库的构建产物**，重建时被 patch 改写（与 `tenant_data.apply_overrides()`
改写 `0wuztp2.9oz~8.js` 同理）。所以仓库里这份现在带的是新配色。

## 影响范围

只改了一处配色表达式，且该组件**只被 Service Ops 页引用** —— 见下表。

| 场景 | 预期 | 实际 | 状态 |
|---|---|---|---|
| 30 格实际背景色分布 | 28 绿 + 2 黄 + 0 红 | `rgba(16,185,129,0.4)` ×21、`rgba(16,185,129,0.65)` ×7、`rgba(245,158,11,0.85)` ×2 | OK |
| 红色档 `rgba(244,63,94)` 在热力图表达式里 | 消失 | 表达式里已无（bundle 里其余 8 处是别处的玫瑰色，非热力图） | OK |
| Business Ops (`/biz-ops`) | 不受影响 | 其 chunk `00tsl~72wvlrr.js` 对 `Heatmap` **零引用**，页面 DOM 里也没有这种网格 | OK |
| Constellation (`/constellation`) | 不受影响 | 同上，零引用 | OK |
| Service Ops 页其余功能 | 不受影响 | 回归 15/16（唯一失败是既有的 `/domain-config` 无路由 bug，非本次引入） | OK |
| console | 无 error | 0 个 | OK |
| 重建幂等 | 重复构建不叠加 | 第二次构建 patch 返回 False（`HM_REPL in t`），不重复改写 | OK |
| 站点改版后 | 静默跳过而不是改坏 | `t.count(HM_FIND) != 1` 时返回 False | OK |

### 为什么只影响 Service Ops

`Heatmap` 定义在共享 chunk `100pim9o6kpoy.js` 里，但：

```bash
grep -oF "Heatmap" public/_next/static/chunks/*.js
#   0t1fyt7wcotiz.js: 1 次     ← Service Ops 组件（引用）
#   100pim9o6kpoy.js: 1 次     ← 定义本身
```

Business Ops 的 `00tsl~72wvlrr.js` 与 Constellation 的分享池**都是零引用**，
两页的 DOM 里也都查不到第二处这种网格。所以这个替换实际上只作用于服务概览页。

## 踩坑记录

| 坑 | 现象 | 根因 | 处置 |
|---|---|---|---|
| **以为改数据就行** | 调小几个值，红的还是红 | 归一化是**相对**的（min-max 取自本序列），最大值恒为 `o=1` → 恒在最高档 | 只能改阈值。已在 `patch_heatmap_palette` 的 docstring 里写明 |
| **改完看不到效果** | 磁盘与 dev server 都已是新表达式，页面颜色却不变 | 浏览器缓存了 chunk（iframe 内的文档有独立缓存） | CDP 里 `Network.clearBrowserCache` + `setCacheDisabled`。**验证配色改动必须清缓存** |
| 用 `rgba(244,63,94)` 计数判断"红色还剩几处" | 得到 8 而非 0，一度以为没改上 | 那是 bundle 里**别处**的玫瑰色（KPI 数值色等），不是热力图 | 改为只看热力图那条表达式内部，并运行时按实际 `backgroundColor` 分类统计 |

## 怎么用

```bash
python3 tools/make-offline-page.py --page service-ops   # 重建，会打印「热力图配色：…」
npm run dev                                              # 顶栏点 Service Ops，滚到底
```

> 想再调（比如要 1 个黄、或换个绿色深浅），只改 `tools/tenant_copy.py` 的 `HM_REPL`
> 里的阈值即可 —— `o<.9` 那个数字就是"从第几名开始变黄"的闸门，调大 = 更少黄。
