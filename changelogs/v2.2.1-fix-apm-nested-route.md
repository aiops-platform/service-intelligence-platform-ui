# v2.2.1 — 修复：APM 两个页面（Monitor Targets / Domain Rules）点不开

**日期**: 2026-09-16

**问题**: `Service Ops › Observability › APM` 下的 `Monitor Targets` 与 `Domain Rules`
两个菜单，点击后页面不切换，仍停在 Service Ops 概览页 —— 表现为「这两个页面不见了」，
但实际上面板、模态、`initMonitorTargets()` / `initDomainConfig()`、`_pageRefreshers`
刷新钩子全部完好，一个字节没少。

用户一度怀疑是「本地改动没提交」。已排除：工作区干净、无 stash、历史无删除记录、
三个分支 reflog 连续。

## 根因

`flattenItems()` 是路由表的唯一来源（`src/router/index.js:161`），但它**不递归嵌套分组**。

`nav.js` 里 `groups` 与 `items` 在**分组对象上平级**，从来不是 item 的字段；
而旧实现的 `if (it.groups)` 写在了遍历 **items** 的循环里，那个分支永不成立：

```js
// before —— walk 收到的是 item 数组，item 上永远没有 .groups
const walk = (items) => {
  for (const it of items) {
    if (it.slug) out.push(it)
    if (it.groups) for (const g of it.groups) walk(g.items)   // ← 死分支
  }
}
for (const top of nav) {
  if (!top.sidebar) continue
  for (const g of top.sidebar.groups) walk(g.items)   // ← 只有顶层分组被走到
}
```

于是 `APM` 这个**子**分组底下的两个叶子从未进入返回列表，`flattenItems()` 只产出 14 个
叶子（应为 16）。`/monitor-targets` 与 `/domain-config` 两条路由根本没生成 →
落进 `router/index.js:165` 的 catch-all → `redirect: '/service-ops'`。

**菜单画得出来**（`SidebarGroup.vue` 有自己的递归渲染，是对的），**路由却产不出来** ——
这就是「看得见、点不动」的来源。且因为是 `redirect` 而非 404，全程无任何报错。

## 改动明细

### 1. `src/router/nav.js:238` — `flattenItems()` 改为递归分组 (line 238-249)

**原因**: 递归对象搞错了 —— 该递归的是分组，不是 item。

```js
// before
const walk = (items) => {
  for (const it of items) {
    if (it.slug) out.push(it)
    if (it.groups) for (const g of it.groups) walk(g.items)
  }
}
for (const top of nav) {
  if (!top.sidebar) continue
  for (const g of top.sidebar.groups) walk(g.items)
}

// after
const walkGroup = (g) => {
  for (const it of g.items) if (it.slug) out.push(it)
  for (const sub of g.groups || []) walkGroup(sub)
}
for (const top of nav) {
  if (!top.sidebar) continue
  for (const g of top.sidebar.groups) walkGroup(g)
}
```

遍历顺序与 `SidebarGroup.vue` 的递归渲染保持一致（先 `items` 后 `groups`），
子分组叶子排在父分组叶子之后。

**此修复只动这一个函数，legacy 侧零改动** —— 两条路由的 `meta.legacy`（`!MIGRATED.has(slug)`
= `true`）与 `panelId`（`PANEL_ID` 里早就有 `page-monitor-targets` / `page-domain-config`）
都是现成的，`router/index.js` 的 `afterEach → __SIP_SHOW_PAGE` 链路随即把面板点亮。

**顺带修好 `navKeyOf()`**（`nav.js:275` 复用同一函数）：此前它对这两个 slug 返回 `null`，
靠 `App.vue` 的 `?? 'service-ops'` 兜底碰巧对；现在返回真值。`/runs/:runId` 仍返回
`null`（未受影响，`App.vue:54` 的域外守卫依赖这一点）。

### 2. `package.json:4` — 版本号 2.2.0 → 2.2.1 (line 4)

**原因**: 按仓库约定，changelog 与版本号同一次提交（见 `40794f3` 的 file list）。

## 踩坑记录

**1. 「工作区干净」不等于「功能正常」。** 这次用户的第一反应是「是不是我没提交」。
排查顺序应该是：先确认代码存在（`grep` 面板 id / init 函数）→ 再确认路由产出
（`flattenItems()` 有没吐出这个 slug）→ 最后才怀疑后端/数据。直接从 git 入手会绕远路。

**2. `redirect` 型 catch-all 会把「路由缺失」伪装成「页面正常」。**
`/monitor-targets` 无匹配时不是 404，是静默重定向回 `/service-ops`，
控制台一行错误都没有。**静态看路由表最容易漏这种**，只能靠实跑。

**3. 验证「哪个面板可见」时别用 `'display:none' not in html`。**
浏览器序列化 CSSOM 时会输出 `display: none;`（**带空格**），而未被 JS 触碰过的元素
保留原始的 `display:none;`（不带）。同一份 DOM 里两种写法并存，字符串匹配会误判。
另外**唯一没有 inline `style` 属性的面板是 `#page-service-ops`**（源文件里就没写），
它会被一切「没有 display:none 就算可见」的检查误报成可见 —— 它是否真的可见取决于
祖先 `#sip-legacy-host` 上的 `v-show`。正确的做法是解析 `style` 属性取值、
并考虑祖先链。

**4. 排查期误杀 dev server。** 用 `pkill -f vite` 清理临时起在 5174 的实例时，
把用户原本跑在 5173 的进程一起匹配掉了。**清理自己的进程要按端口定位**
（`lsof -ti:5174`），不要按进程名通配。
