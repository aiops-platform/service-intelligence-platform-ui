# v2.6.5 — View diagnosis 的「处理 · DECISION」展示工单回传的处置结论；问题单转 resolved 后这张卡不再消失

**日期**: 2026-09-22

**需求**: 「当 ticket 通过接口给我们返回 ticket 处理结果的时候（`{"type":"ticket_status","status":"resolved",
"ticket_id":…,"description":…,"reported_at":…}`），View diagnosis 弹出框的**处理 · DECISION** 这一块
来展示它的 `description` 以及 `reported_at`。并且状态变更为 resolved 时，**处理这块是不消失的**。」

---

## 背景：回传的结论**没有任何界面入口**

`aiops-apm-anomaly-detector` 侧的回传闭环（design-v5.8 §13）早已实施：升级派单 →
agentflow 跑修复工作流 → `ticket-done` 把结论 POST 回 `/v1/problems/ticket-status` →
落成一条 evidence，`resolved` 时顺带把问题单从 `escalated` 改成 `resolved`。

前端的问题是**这条 evidence 谁都不读**，而且卡片的显隐判据恰好把它挡在门外：

```js
// 改前 js/app.js:4976（dgxApproval 开头）
if (recState === 'escalated') { …结果卡，只印单号… }
if (recState !== 'pending' && recState !== 'in_progress') return '';   // ← resolved 落在这里
```

于是「处理 · DECISION」在 resolved 的记录上**整块消失**，而消失的正是人最想看结果的那一刻
（派出去的那张单修得怎么样了）。实测（真库 `PR-20260922-0001`，`agentflow:resolved:INC-20260922-0002`）：

```
labels: ["根因 · ROOT CAUSE","总结 · SUMMARY","修复方案 · FIX OPTIONS","历次执行 · EXECUTIONS","历史计划 · PLAN HISTORY"]
```

—— 没有「处理 · DECISION」，`description` 与 `reported_at` 在界面上无处可见（只在 Problem Detail 的
evidence JSON 里躺着）。

---

## 改动明细

### 1. `js/app.js:4604` — 新增模块状态 `dgxTicket`

```js
var dgxTicket = null;     // 当前记录的工单：派单号 + 回传的处置结论（见 dgxTicketOf）；没派过单 → null
```

与 `pcDiagHistory` 同处一组（都是「当前弹框记录的派生数据」），开弹框时整体复位。

### 2. `js/app.js:4780` — `dgxTicketOf(rec)`：记录 → 工单对象

```js
var number = problemTicketNumber(rec);   // 派单号：真源 = escalate 裁定的 evidence
// 取**最后一条** ticket_status：一轮跑完一条，重跑就再来一条，最后一条才是工单现在的状态
```

`{number, status, description, reported_at}`；**没派过单返回 `null`** —— 这时处理卡才走审批按钮那条路。
单号与结论都读自 evidence（不是本地临时值），所以**重开弹窗、换台机器看到的都一样**。

### 3. `js/app.js:4992` — `dgxTicketCard(tk)`：工单卡

```js
已升级——本次诊断已转成一张修复工单，工单号 INC-20260922-0002。
回传状态  已修复
处置结论  根因：order-service 的 QuotationService.quotationSummary …
回传时间  2026/09/22 17:19:19
```

- 状态三档**绝不印原始枚举**（与 `DGX_DECISION_LABEL` 同纪律）：
  `DGX_TICKET_STATUS = { resolved: '已修复', failed: '修复未完成', insufficient: '证据不足' }`。
  漏登记的回落原值 —— 看得见比看不见好。
- **未回传时只留第一句**（工单还在跑）：不用占位文本撑版面，那看起来像"结果丢了"。
- 时间走本页既有的 `formatTime`（按 UTC 解析、以 Asia/Shanghai 显示），与表格里的时间同口径。
- 全部复用既有类 `.dgx-card/.dgx-approve/.dgx-label/.dgx-approve-hint/.dgx-kv/.dgx-k/.dgx-v/.dgx-mono`，
  **无新样式**。

### 4. `js/app.js:5016` — `dgxApproval()`：判据从 `state` 换成「有没有工单」

```js
// before
if (recState === 'escalated') { …从 pcDiagHistory 里找最后一条 escalate 裁定… }
// after
if (dgxTicket) return dgxTicketCard(dgxTicket);
```

**为什么必须换判据**（本版的核心）：回传 `resolved` 会把问题单转成 `resolved`，按 `state` 判的话
这张卡连同处置结论一起消失。改成「记录里有没有工单」之后，`escalated` 与回传后的 `resolved`
**同一张卡、同一条判据** —— 状态怎么翻都不会掉。

顺带修掉一个旧限制：单号原先取自 `pcDiagHistory`（异步拉的历史计划），首屏可能**先无号**、
等 `loadDiagnoseDecisions` 回来才补上；现在单号直接在记录 evidence 里，开弹框即有。

### 5. `js/app.js:4732` — `syncOpenDiagnosis()`：搭列表那趟 5s 轮询的车

弹框开着的时候后端照样会改记录（回传写入 evidence + `escalated → resolved`），而 `pcDiagRec`
是开弹框那一刻抓的旧对象。本函数挂在 `refresh()` 的成功分支里（`js/app.js:6336`）：
列表每 5s 静默重拉一次，**顺手**把当前记录换成本轮那份、重算工单、变了才重渲染。

- **不额外发请求** —— 列表轮询本就在跑（页面可见时）。
- **没变不重渲染**（`dgxSameTicket`）：`renderDiagnosis` 是重建整块 DOM，白重渲染会把滚动位置
  和展开着的「历史计划」`<details>` 一起重置。
- 记录在本轮列表里找不到（被筛掉/删了）→ 保持现状，**不把弹框清空**。

### 6. `js/app.js:5128` — 升级那一步就地落 `dgxTicket`

```js
pcDiagRec.state = 'escalated';
dgxTicket = { number: num, status: '', description: '', reported_at: '' };  // 单号先用响应里的
```

不落的话，升级瞬间卡会**空一拍**（记录 evidence 还没回到前端，`dgxTicket` 还是 null → 掉进
`state` 分支 → escalated 不满足 pending/in_progress → 返回空串）。下一轮列表刷新会用 evidence 里
同一份号覆盖，值相同 → 不重渲染，不会闪。

## 未处理

1. **只显示最后一条回传**。同一次升级可能因为重跑产生多条（实测那条有两条，分别对应 PR #7 / PR #8）。
   卡上取最后一条（工单当前状态）是有意为之；要回看每一条，入口是 Problem Detail 的 evidence 列表。
   若以后需要「回传历史」，形状应与「历史计划 · PLAN HISTORY」一致（独立的只读端点 + 折叠条目），
   而不是把卡撑成列表。
2. **`description` 里的换行会被 HTML 折叠**（`.dgx-v` 是普通文本流）。当前实测的结论都是一整段，
   与历史计划里的「拒因」同款处理（那里也是直接 `dgxEsc`）。真出现多段文本再加 `\n → <br>`。
3. **回传不触发通知**：卡片是"静默更新"的（搭 5s 轮询的车）。人若没开着弹框，只有在列表上看到
   状态列变成 `resolved` 才知道修完了。要不要给一次 toast，等需求方定。
