# v2.6.13 — Diagnosis Center：halt 后给「补齐证据重跑」入口（原先只剩「忽略/升级」）

**日期**: 2026-09-23

> 本文行号指**本次改动后**的当前文件。本次改动**依赖后端同时改动**（见文末「跨仓依赖」），
> 两侧判据同源，缺一边按钮就是白点。

**问题**: 日志分析 workflow 有显式的**中断终点** `halt`（触发条件：`rca.insufficient == true`
或 `locate.found == false`）。中断后 run 终态是 `done`、结论为空 —— 于是：

1. `canReject = (st === 'completed') && hasSteps` **必然为假**（没有方案就没有 steps）→
   「拒绝 · 重新分析」不显示，只剩「忽略」和「升级 · 修复流程」，**两个都不能重跑**，
   用户卡死在"证据不足但没法让它再跑一次"。
2. 即便点了「拒绝」，后端此前**也没把人填的 `feedback` 送进新一轮 run 的输入** ——
   输入与上一轮逐字节相同，缺的证据没变，重跑必然再次 halt。UI 那句 placeholder
   「诊断将带着这条建议重新分析…」是**空头支票**。

## 改动明细

### 1. `js/app.js:5084-5101` — `canReject` 放宽（halt **与** failed 都算）+ 按钮文案随语义切换

**原因**: 无结论时没有"方案"可驳，但**恰恰最需要带着人的补充线索再跑一轮**。
后端两条走的是**同一条 reject 分支**（起新一轮 run），不依赖方案、也不依赖有待批的门。

```js
+ var noConclusion = opts.length === 0;
- var canReject = (st === 'completed') && hasSteps;
+ var canReject = (st === 'completed' || st === 'failed') && (hasSteps || noConclusion);
+ var rejectLabel = hasSteps
+     ? '拒绝 · 重新分析'
+     : (st === 'failed' ? '重试诊断' : '补齐证据重跑');
```

**`failed` 那一档是补的**（原先只认 `completed`）：run 直接**失败**（LLM 出站挂掉、abort 节点）
同样没有结论，而这类环境/瞬时故障最该一键重试 —— 却只剩「忽略 / 升级 · 修复流程」。
后端对 failed 与 halt **判定完全同路**（无门 → `no_pending_gate` → 起新一轮，理由同样选填），
实测把 reject 发在 failed 的 run 上返回 200 并起了新 run（`run_4b7b649bef` → `run_a5ab9555a3`）。
文案也单列一档：failed 说"补齐证据"是误导（人多数只需再跑一次，而不是先去找线索）。

### 2. `js/app.js:5108-5116` — hint 分 halt / failed 两种说法

**原因**: 原文案"可忽略或升级到修复流程"漏了新增的第三条路；且"证据不足中断"套在 failed 上
会把人引去补证据 —— 那是**这一轮没跑完**，不是"跑完了但证据不够"。

```js
- : '本次诊断未给出可执行方案，可忽略或升级到修复流程。';
+ : (st === 'failed'
+     ? '本次诊断未跑出结论（执行失败）：可直接重试、忽略，或升级到修复流程。'
+     : '本次诊断未给出可执行方案（多为证据不足中断）：可补齐线索重跑、忽略，或升级到修复流程。');
```

**原因**: 从前的 placeholder 是**假承诺**（后端没把 feedback 送进新一轮）。现在它真的会带进去，

## 踩坑记录

1. **"无结论"是一个前端看不见后端拦的典型夹缝**：UI 放行了空反馈，但后端
   `_decide_agentflow` 里那条"拒绝必须带修改建议"会 400 —— **只改前端等于点了就报错**。
   本次两头一起改，且判据同源：后端用 `from_agentflow.conclusion_digest(run)` 是否为空
   （halt/失败时返回 `{}`，且与**页面上显示的结论同源**），前端用 `conclusion.recommended_fix` 长度。
2. **判据取"服务端事实"而不是"客户端点了哪个按钮"**：后者可被伪造（curl 直接传空反馈就能绕过守卫），
   前者不能。代价是那条校验挪到了 `GET /runs` 之后 —— 注定 400 的请求会多一次出站，可接受。
3. **legacy 脚本的产物位置**：`js/app.js` 是**原样复制**到 `dist/js/app.js` 的（不走 Vite 打包），
   所以文案改动**不会**出现在 `dist/assets/index-*.js` 里 —— 别按 chunk 里的关键字判断改动有没有生效。
4. **"留空 = 直接重试"不等于"清空线索"**：后端那行是
   `inputs["review_feedback"] = (body.feedback or "").strip() or inputs["review_feedback"]`
   —— 留空时会**沿用 evidence 里上一轮的线索**（本轮值优先）。对"同一份缺失反复重试"这是想要的，
   但它没写在任何 UI 文案里，别把它当 bug 报（要清空就得显式写点什么）。
5. **本功能的"目标"还差一层，而且不在本仓**：把建议送到位（本 changelog + 后端）只解决了
   "输入一样"那一半。实测（`run_a5ab9555a3`）带线索重跑**仍然 halt** —— 根因是
   `locate` 用的 `search_code`（git-mcp-server）**默认走 BRE**，`a|b|c` 这种交替查询被当字面量
   → **0 条命中且不报错**。而 `code-locator` 的提示词**强制**它"以 search_code 的返回为准"核实路径，
   于是它一遍遍换关键词、把 10 轮预算烧光 → `locate` 判负 → halt。**提示词治不了工具说假话**：
   同一仓库 `git grep "generateQuotation|renderItems"` 空、加 `-E` 命中 29 条。
   → 修在 agentflow 仓的 `search_code`（见「跨仓依赖」），且**必须重启该 MCP server 才生效**。
   （2026-09-23 17:10 已改并重启验证：同仓交替查询从 0 条 → 29 条命中；随后 `run_6e9618dce4` 跑通，见影响范围表。）
6. **「起 run 超时」会让新一轮变成孤儿 —— 而且它是静默的**：APM 起 run 的响应超时是
   `run_start_timeout_sec`（默认 **60s**，`settings.py`），而 agentflow 的 `POST /run` **同步**
   准备各服务工作区（`git ls-remote` 打 GitHub）。本机 GitHub 不通（代理没起）→ 单仓 75s 才失败
   → 60s 先到 → APM 返回 `UPSTREAM_ERROR` 且**没追加 `agent_run` evidence** → run 照跑完
   （结论齐全！），但问题单**不知道它存在**：UI 仍显示旧那一轮，人看着像"点了没反应"。
   更坑的是那条错误文案劝人"check this problem's evidence/run before retrying"——
   **而 evidence 里什么都没有**（本轮实测）。
   → 要么把代理起起来让 GitHub 可达（prep 秒回，超时自然不触发），要么把超时调大，
   要么让超时路径也能把 run 绑回去（真正的修法在"同步 prep"本身）。
