**日期**: 2026-09-15

奔驰经销商集团的 50 个应用 / 11 个业务组合 / 2 条客户旅程。用户提供 Enterprise、Journey、

## 改动明细

### 1. `tools/tenant-gen/build_mb_retail.py` — 新增：租户生成器

**原因**: 用户只给四层节点，但 `snapshot` 里除 `apps`/`portfolios`/`journeys`/`enterprise`
之外全是**独立结构、不会自动派生**的字段（`facts`、`portfolioEdges`、`appTechnologies`、
`valuePool`、`scenarios`、`agents`、`sparkline90d`、`topStorm`），必须单独生成。

坐标沿用从 retail 实测反推的公式：

```python
# journeys/portfolios：等分角度，起点 270°
# apps：r = 480 + (tier-1)*90 + U(0,150)，角度 = 所属 portfolio 角度 ± 11°
r = 480 + (a["tier"] - 1) * 90 + RNG.uniform(0, 150)
a["position"] = pol(r, p["angle"] + RNG.uniform(-11, 11))
```

`appKey` 沿用用户自己给出的命名习惯 —— **label 唯一时只用 slug，跨组合时加 `-<组合>` 后缀**：

```python
a["_derived"] = base if seen[a["label"]] == 1 else f"{base}-{slug(a['portfolio'])}"
# 用户显式给的 appKey 只在「自己不冲突」时才采纳
```

### 2. `tools/tenant-gen/mb-retail.raw.json` — 新增：用户提供的四层节点（原始输入）

### 3. `tools/tenant-gen/validate.py` — 新增：差分校验器

**原因**: 手抄 zod schema 的校验漏掉了 `portfolios[].journey` 的类型（坑 9），导致白屏。
改为**以已知能跑的租户为基准做结构差分** —— 活的标准答案不会漏。

```bash
python3 validate.py mb-retail [--ref retail]
```

比对每个字段路径的类型，另查：`z.string()` 非 nullable 字段、枚举值（agent mode）、
`portfolioId` 悬空、`id`/`appKey` 重复、`taxonomy` 与 `snapshot` 的 tier 一致性、
`appArchetypes[].tier` 必须是字符串。schema 里没有但基准有的字段（`replay-storm.anchor` /
`timeline`）列为已知死字段，不报错。

### 4. `tools/tenant-data/mb-retail.json` — 新增：生成的租户覆盖文件（74 KB）

`make-offline-page.py` 构建时自动注入 bundle，不碰源文件，删掉即可回退。

### 5. `tools/tenant_copy.py` — 新增：按租户改写写死的外壳文案

**原因**: 页面有一批文案写死在客户端代码里，锚定在 Acme Retail / data-sicg 的数据上，
切租户不跟着变。最明显的是副标题 `The Acme Retail operational fabric · 282 apps…`。

**为什么不能构建时替换** —— 租户是**运行时**选的：

```
?tenant=<id>  →  localStorage["sip-active-tenant"]  →  兜底 "retail"
```

烤死任何一个租户，切到别家就是错的。所以构建时把**每个租户**的文案算好注入
`window.__SIPCOPY__`（11 租户 × 十几条），运行时按 active tenant 改写 DOM。

走 DOM 改写而不是给压缩 JS 打补丁 —— 站点更新后字面量变了只是**静默失效**，
不会把页面搞坏。用 MutationObserver 兜住 React 的重渲染（替换幂等，不会自激）。

覆盖 16 类文案：

| 类别 | 例 |
|---|---|
| `<title>` / meta / 副标题 | `SIP · The Constellation · Acme Retail` → 按租户 |
| 加载页 + 搜索框 placeholder | `893 apps · 22 portfolios · 6 journeys · 156 agents` |
| 筛选面板计数 | `All 22` → `All 11`；`22 portfolios across 6 journeys` |
| Key attributes | `Top 10 by incidents · 18M`、`Holiday-critical` |
| 保存视图 | `INC13075702 · 1,809-child blast radius`、`Manhattan WMS · the spotlight node` |
| 叙述 | `Emergency changes back out at 2.34% vs Standard 0.02%…` |

### 6. `tools/make-offline-page.py` — 注入租户文案 + 补切换面板清单

在 3b 之后新增 3c：读**输出目录那份** bundle（此时才含新增租户）→ 注入文案映射 +
改写器；再调 `patch_switcher()` 补切换面板的租户清单。

## 踩坑记录

### 坑 1：`snapshot` 也被 zod 严格校验 —— 文档说反了

`tenant_data.py` 的模块注释写着「`snapshot` 是自由结构」，`validate_snapshot()` 也只查
`apps`/`portfolios`/`journeys`/`facts` 四个键。**这是错的。**

`public/_next/static/chunks/0aed4f89z1emu.js` 里有完整的 zod schema：

```js
let h = ALL_TENANTS[ACTIVE_TENANT_ID]?.snapshot;
if (!h) throw Error(`Snapshot missing for tenant "..."`);
let y = b.parse(h);          // ← 缺字段 / 类型错 → 抛异常 → 白屏
```

**后果**：手写的 snapshot 可以过 `tenant_data.py check`，然后页面白屏。「坑 1 说改完一定
先 check」对 `tenant` 部分有效，对 `snapshot` 不成立。本次因此额外写了一遍按真实 schema
的校验（16 个顶层键 + 嵌套类型 + 枚举值）。

### 坑 2：`portfolioEdges` 是死数据 —— 校验但从不渲染

把源 `_files/`（11 个）与产出 `public/` 的**所有** JS chunk 都搜了一遍：

| 文件 | 出现次数 | 是什么 |
|---|---|---|
| `0wuztp2.9oz~8.js` | 40 | 数据本身（10 租户 × 4 键） |
| `0aed4f89z1emu.js` | 4 | 只有 zod schema 定义 |

**没有任何渲染代码读它。** 曾据字段名推断「共享组合会在图上拉出连线」，是错的 ——
想当然了，实际不画。字段仍必须填对格式，否则 `parse()` 抛异常。

### 坑 3：`replay-storm` 的 `anchor` / `timeline` 不在 schema 里

真实 schema 只有 `label` / `hostPanel` / `acts` / `agentSuggestions`：

```js
d = z.object({label, hostPanel,
  acts: z.array(z.object({id,title,duration,counterTarget,mttrMinutes,rootIncident})),
  agentSuggestions: z.array(z.object({agent,confidence,action,eta,impact,provenance}))})
```

retail 数据里写了 `anchor` 和 `timeline`，但 zod 默认剥掉未知键 —— 它们从不出现在页面里。
`data-sicg` 那份干脆没写，反而更接近真实契约。

### 坑 4：`facts` 与 app 指标差两个数量级

第一版按 `sum(app.incidentsTotal) × 9` 生成，得 48,672。实测量化 retail 后发现口径不同：

| | retail 实测 | 说明 |
|---|---|---|
| `facts.incidents / sum(app.incidentsTotal)` | **123×** | facts 统计全部告警量，不是应用级事件 |
| `facts.changes / sum(app.changeCount)` | **5×** | 同上 |
| `facts.infraIncidents / facts.incidents` | 0.250 | |
| `facts.problems / facts.changes` | 0.101 | |
| `apps / teams` | 5.2 | 282 apps / 54 teams |

校准后 `facts.incidents = 665,184`（50 apps），比例与 retail 完全一致。

### 坑 5：`scenarios` / `agents` 在 9/10 租户里是空的

只有 `data-sicg`（唯一来自真实库的租户）有内容（35 个 agent）。retail 自己全空。
所以它们**不是必填内容**，空着照样渲染。本次照 `data-sicg` 的样子填了一批。

### 坑 6：副标题是服务端写死的，切租户不会变

`vendor/server.html` 的 RSC payload 里：

```
"description":"The Acme Retail operational fabric · 282 apps across 9 portfolios + 6 journeys, ..."
```

**`operational fabric` 不出现在任何 JS chunk 里** —— 客户端从不构造这个字符串，所以它
在 `?tenant=mb-retail` 下依然显示 Acme Retail 的数字。**尚未修复**，见下方「遗留」。

### 坑 7：用户的 `otr-lead-lead` 复制粘贴漏改

原始数据里 `OTR Lead` 在 Lead 和 Consulation 下都写了 `appKey: "otr-lead-lead"`，
`id` 会撞车。用户自己的命名规则（`<应用>-<组合>`）已经给出正解
（`otr-lead-lead` / `otr-lead-consulation`），生成器对冲突的显式 key 退回派生规则。

### 坑 9：`portfolios[].journey` 类型不符 → 白屏（**这是实际发生过的那次崩溃**）

第一版生成器把用户输入的「第几条 journey」序号（整数 `1`/`2`）原样透传成了
`portfolios[].journey`。但真实 schema 是：

```js
o = z.object({id, label, journeyId: z.string(), journey: z.string().nullable(), position})
```

**`z.string().nullable()` —— 整数不合法。** 后果是 `b.parse(h)` 抛 ZodError，整页白屏。
Chrome 显示的是「This page couldn't load. Reload to try again, or go back.」

实测 11 个租户该字段的取值分布，**从来没有整数**：

```
NoneType None          ×102      ← 绝大多数
str      Browse/Buy/Pickup/…  ×21
int      1 ×6, 2 ×5              ← 全是 mb-retail 自己（我引入的）
```

修法是跟 retail 保持一致用 `null`（归属关系已由 `journeyId` 承载）。

**为什么第一版校验没抓到**：照 zod schema 手抄的 Python 校验只查了 `journeyId` 的类型，
漏了 `journey`。手抄 schema 必然会漏 —— 所以改为**和已知能跑的租户做结构差分**。

### 坑 10：`labels` 是可选的，但不给会显示错误话术

`schema` 里 `labels` 标了 `.optional()`，所以不给不会白屏。但 retail 的值是
`peakSeasonNoun: "the Q4 holiday peak"`（圣诞旺季）—— 对经销商是错的。
已补上 `"the plate-change peak"`（上牌月）。给了就要 6 个全给。

### 坑 11：未捕获异常会把后面的**注册代码整段带走**

改写器注入在 `<head>`，首次执行时 `document.body` 还是 `null`：

```js
run();                                       // ← createTreeWalker(null) 抛 TypeError
if (document.readyState === 'loading') {     // ← 永远执行不到
    document.addEventListener('DOMContentLoaded', run);
}
new MutationObserver(...).observe(...);      // ← 永远执行不到
```

**所有兜底注册都没生效**，于是整页文案一条都没改。修法是**先注册全部兜底，再跑第一次**，
并让 `run()` 内部 try/catch 吞掉单次失败：

```js
if (document.readyState === 'loading') document.addEventListener('DOMContentLoaded', run);
window.addEventListener('load', run);
new MutationObserver(...).observe(...);
[0, 150, 400, 900, 1800, 3500].forEach(ms => setTimeout(run, ms));
run();                                       // 最后才跑
```

### 坑 12：`placeholder` 是属性，不是文本节点

搜索框那句 `Search 893 apps · 22 portfolios · 6 journeys · 156 agents …` 写在
`placeholder` 属性里。只走 TreeWalker 处理文本节点会**整个漏掉**。
已改成同时处理 `title` / `placeholder` / `aria-label` 三个属性。

### 坑 13：切换面板的租户清单是写死的 10 条

`0aed4f89z1emu.js` 里：

```js
let c=[{id:"best-buy-reference",label:"Best Buy · reference",…},{id:"retail",label:"Acme Retail",…}, …]
```

Shift+S 的面板直接读它 —— **新增租户不在里面就选不到**。`?tenant=mb-retail` 能打开，
但面板里找不到它。这条 DOM 改写够不着（是 React 的 props），只能改 chunk：
`patch_switcher()` 用括号配对定位数组，把缺的租户**追加**到末尾。

已有条目的 `label` 是手写的（`"Best Buy · reference"` 带后缀，与 `client` 不同），
无法从数据推导，所以只追加、不动现有条目。追加用 `json.dumps` 生成
`{"id":"…"}`（带引号的键）—— JS 对象字面量里合法，已验证 Node 能解析整个数组。

### 坑 8：`taxonomy.appArchetypes[].tier` 是字符串

`schema` 里是 `z.enum(["T1","T2","T3"])`，而 `snapshot` 和 `taxonomy.portfolios` 的 tier
是数字 `1~3`。写 `1` 会直接 zod 白屏。且 `taxonomy.portfolios[].tier` 与
`snapshot.portfolios[].tier` 是**同一批值重复存了两份**，改了要同步。

### 崩溃排查过程（供下次参考）

改完 `tenant-data/mb-retail.json` 后打开页面 → Chrome「This page couldn't load」。
定位路径：

```bash
# 无头 Chrome 抓 console —— 比猜快得多
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless=new --disable-gpu --enable-unsafe-swiftshader \
  --virtual-time-budget=12000 --user-data-dir=/tmp/cr \
  --enable-logging=stderr --v=1 --dump-dom "<url>" > /tmp/dump.html 2>/tmp/chrome.log
grep -i "CONSOLE\|uncaught\|ZodError" /tmp/chrome.log
```

拿到了 `"Uncaught ZodError"`。**注意 macOS 没有 `timeout`**（那是 GNU coreutils），
加了会 exit 127。WebGL 在无头下会拖慢退出，`--virtual-time-budget` 到点后会挂住，
用后台任务跑 + 直接读日志文件即可 —— console 输出在头一两秒就写完了。

## 遗留

1. ~~副标题未修~~ —— **本轮已修**（`tenant_copy.py`，见改动明细 5）。
   原本实测 `Acme Retail` 在 DOM 里出现 4 处：`<title>`、RSC payload ×2、
   以及**可见正文** `<p>The Acme Retail operational fabric · 282 apps across 9 portfolios…</p>`。
   现在按 active tenant 运行时改写，11 个租户都正确。

2. **`All 13` 没动** —— 筛选面板的边类型计数。查了 `0p_dozb5cvong.js` 里的边类型清单
   **只有 9 条**，所以 `13` 既不等于清单长度、也不随租户变，是上游自己写死的常量
   （可能还混了别的边种类）。不是租户不匹配问题，改它反而可能改错，保持原样。

3. **`Emergency changes · 6% rate` 没动** —— 这个百分比在 `facts` 里没有对应字段
   （只有 `emergencyBackoutRate` 等退单率），推导不出来，宁可留着也不编。

2. **`tenant_data.py` 的 `validate_snapshot()` 与真实契约脱钩**（坑 1）。
   建议补成真校验，否则「过 check」和「页面能跑」是两件事。

3. **`topStorm` 锚在 `SPM`（Parts）**。T1 里事件数最高的 5 个是
   `SPM` 211 / `Xentry` 210（风险 98）/ `OTR Campaign` 186 / `OTR Parts Sales` 184 /
   `DSR` 165。奔驰场景下以 `Xentry` 作主角更好讲，要换改一行。

4. **数据里的命名**：`Consulation`（应为 Consultation）、`Customer Server Journey`
   （应为 Service）、`Mystar`、`OTR Lead` 的 label 未加组合后缀。用户确认只改
   `accounting` 和 `otr-parts stock` 两条。
