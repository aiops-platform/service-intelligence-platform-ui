# v2.0.0 — Business Ops 支持非 6 条 journey 的租户

**日期**: 2026-09-15

**问题/背景**: 给 MB Retail（2 条 journey）做演示时，Business Ops 页面在 journey 表里
渲染出 **4 行空占位** —— `Journey 3` … `Journey 6`，各 0 apps。

---

## 首要澄清：Business Ops **没有**独立数据集

排查时先确认了一件事，值得记下来：

```
0pfw3-ib1qee0.js (Business Ops)  →  t.i(23406).snapshot
0aed4f89z1emu.js (Constellation) →  e.s(["snapshot",0,y],23406)
0wuztp2.9oz~8.js                 →  ALL_TENANTS[ACTIVE_TENANT_ID].snapshot
```

**两个页面读的是同一个模块 23406，也就是同一份 `snapshot`。** Business Ops 读的字段：

| 字段 | 用途 |
|---|---|
| `apps` | 按 portfolioId / holidayCritical / operationalStatus 过滤聚合 |
| `portfolios` | 按 journeyId 归组 |
| `journeys` | `find(e => e.id === \`journey:${n}\`)` 取标签 |
| `facts` | `monthsCovered`、`topAlertStormChildren` 等 |
| `sparkline90d` | 热力图（周数 `c` 由日期跨度**动态算**，非写死） |
| `scenarios["ask-sip"]` | Ask SIP 的预设提问 |
| `topStorm` / `source.asOf` | inspector |

所以**新租户不需要为 Business Ops 单独建数据** —— 写进 `tenant-data/` 的那份同时驱动两页。
`100pim9o6kpoy.js` 里的 `AGENTS`（156 条 agent 目录）是**独立的非租户数据集**，
且在 Business Ops 页面上一条都没渲染（实测 `Storm Detector` / `INC13075702` / `1,809` / `95.4%`
均为 0 次）—— 那是给 `/agents` 页用的共享 chunk。

---

## 改动明细

### 1. `tools/tenant_copy.py` — 新增 `patch_journey_slots()`

**原因**: journey 表的行数是写死的。

```js
function u(t){ let n=e.snapshot.journeys.find(e=>e.id===`journey:${t}`); return n?.label??`Journey ${t}` }
let h=[1,2,3,4,5,6].map(t=>d(u(t)…))        // ← 固定 6 个槽位
```

原有 **10 个租户恰好全是 6 条 journey**（retail/banking/bunnings/… 无一例外），
所以这个写死从没暴露过。租户少于 6 条时，多出来的槽位查不到就退回字面量
`Journey ${t}`，渲染成空行。

**不改数据去迁就硬编码** —— 为凑够 6 行编造 4 条 journey 会伪造客户的业务结构。
改成按数据自适应，对任何租户都成立：

```python
JOURNEY_SLOTS_FIND = "let h=[1,2,3,4,5,6].map("
JOURNEY_SLOTS_REPL = "let h=e.snapshot.journeys.map((_,i)=>i+1).map("
```

`e` 在该作用域就是模块 23406（snapshot），`u(t)` 按 `journey:${t}` 查表，与下标 +1 一致。
全文件只有 **1 处**匹配，`count() != 1` 时静默跳过（站点改版不会把页面搞坏）。

### 2. `tools/tenant_copy.py` — 新增 `across 6 journeys` 替换

`00tsl~72wvlrr.js` 的 "Avg Journey XLA" KPI 副标题：

```js
sub: `across 6 journeys · ${Math.round(T)} incidents/day estate-wide`
```

后半段是算出来的，前半段的 `6` 写死。加进 `LEGACY` 映射，按 `facts.journeys` 替换
（retail 的 6 与原文相同 → 不产出替换对，保持原样）。

### 3. `tools/tenant_copy.py` — 新增 `patch_cross_journey()`（桶空则隐藏该选项）

**原因**: 域选择器里有一项 `Cross-Journey`，是**兜底桶** —— 装 `journeyId` 为
`null` / `"journey:null"` / `""` 的组合（企业级支撑组合，本来就不挂客户旅程）：

```js
m = d("cross-journey", "Cross-Journey", "Cross-Journey",
      "Shared capabilities serving multiple BBY journeys · Product · Fulfillment · …",
      t => null==t || "journey:null"===t || ""===t)
```

但它**永远显示**，即使桶里 0 个组合。mb-retail 的 11 个组合全部挂了 journey，
点进去是空的。

**不能无条件删** —— 实测各租户的桶内容：

| 桶里有内容 | 桶是空的 |
|---|---|
| best-buy-reference (1)、bunnings (5)、qantas (4) | banking · consumer-goods · healthcare · insurance · life-sciences · mb-retail · **retail** · telecom |

改成数据驱动，对任何租户都成立：

```python
CJ_FIND = ',{id:"cross-journey",label:"Cross-Journey"}]'
CJ_REPL = (',...(e.snapshot.portfolios.some(p=>!p.journeyId||"journey:null"===p.journeyId)'
           '?[{id:"cross-journey",label:"Cross-Journey"}]:[])]')
```

判据直接内联原来那句（`!x` 覆盖 null/undefined/`""`），**不依赖 `m` 的返回结构** ——
`m` 是用逗号链式声明的（`,m=d(...)`），查它的 return 形状不如内联来得稳。

> ⚠️ **这个改动波及 8 个租户**，包括默认租户 retail（它的桶也是空的）。
> 即「隐藏一个点进去什么都没有的选项」—— 行为上更正确，但确实改变了这些租户的外观。

### 4. `tools/tenant_copy.py` — 新增 `patch_ask_sip()`（隐藏 Ask SIP 卡片）

**需求**: 隐藏 Business Ops 面板末尾的 "Ask SIP · Operational executive view" 卡片。

组件 `g()` 的返回**不是普通的 `return jsx`，而是一个逗号表达式**：

```js
return (0,r.useEffect)(()=>{h.current&&(…)},[e,l]), (0,t.jsxs)(n.Card,{className:"mt-4", …})
//     └─ 副作用（注册自动滚到底）              └─ 真正被返回的那个
```

所以往第二个操作数前面插 `null&&`：

```js
return (useEffect(…), null && Card)   →   null
```

**hooks 仍然在 return 之前照常执行**，不破坏 hooks 顺序 —— 比「让组件整体
`return null`」更稳（后者要挪动 hooks 位置）。Node 桩验证：

```
g() 返回: null
hooks 仍执行: true
```

**作用范围**: 只在 Business Ops 出现（实测 Constellation 页面的 DOM 里 `Ask SIP` 为 0 次）。
`00tsl~72wvlrr.js` 是两页共享 chunk，所以替换对两页都生效 —— 对 Constellation 无影响
（它本来就不渲染这张卡片）。**这个隐藏对所有租户生效**（不是按租户条件）。

### 5. `tools/make-offline-page.py` — 调用新 patch

在 3c 里依次调用 `patch_switcher()` / `patch_journey_slots()` / `patch_cross_journey()`，
随构建幂等执行（每个都有「已打过就跳过」+「匹配数≠1 就跳过」双重保护）。

## 踩坑记录

### 坑 1：为什么之前没发现

排查时先怀疑是「数据缺 journey」，但扫描 10 个租户发现**全部是 6 条** —— 这不是巧合，
是页面按 6 设计、数据也按 6 造的。所以**租户数不等于 6 时才会暴露**，而 MB Retail 是第一个
非 6 条的租户。这类「所有样本都恰好满足」的隐式约束，只能靠引入一个不满足的新样本来发现。

### 坑 2：`[1,2,3,4,5,6]` 只出现一次，但影响整页

原本担心这个数组被多处复用（改了会波及别处）。实测 `grep` 全目录只有
`0pfw3-ib1qee0.js` 一处 —— 所以替换是安全的。**先数匹配次数再改**，不要凭「看起来像通用常量」
就以为它到处都是。

### 回归为什么可以证明而不只是「测过」

改动只碰了数组字面量，`.map(t=>…)` 之后的函数体一字未动。所以回归风险**完全等价于
「新旧表达式是否产出同一个数组」** —— 这个可以在 Node 里穷举证明，比跑浏览器更硬：

```
retail        journey 数 6 → 新 [1,2,3,4,5,6]  旧 [1,2,3,4,5,6]  相同 ✓
banking       journey 数 6 → 新 [1,2,3,4,5,6]  旧 [1,2,3,4,5,6]  相同 ✓
life-sciences journey 数 6 → 新 [1,2,3,4,5,6]  旧 [1,2,3,4,5,6]  相同 ✓
mb-retail     journey 数 2 → 新 [1,2]          旧 [1,2,3,4,5,6]  不同（预期）
```

**6 条 journey 的租户产出的数组逐元素相同 → 行为不可能变。** 剩下 10 个租户全是 6 条，
所以这覆盖了全部回归面。（顺带一提：这也是「改最小面」的好处 —— 如果替换的是一个
含逻辑的表达式，就没法这样证明了。）

   换了租户后提问内容变了、回答还是原来那套，**问答对不上**。
   实测在 Business Ops 默认视图里不渲染（要点预设问题才出），故本次未改。

   （`INC13075702 with 1,809 child incidents`、`canonical WMS 95.4% signal`）。
   该目录是跨租户共用的静态目录，Business Ops 不渲染它 —— 但如果做 `/agents` 页演示会露出来。
