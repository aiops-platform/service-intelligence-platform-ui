# v2.2.7 — 修 `deriveStatus()` 引用未声明变量 `disk` 导致的整页崩溃

**日期**: 2026-09-18

**问题/背景**: 在做 Smart Inspection 两列改造（`v2.2.7-si-problem-counts.md`）时顺带发现的
既有 bug。`deriveStatus()` 里引用了**从未声明**的 `disk`：

```js
function deriveStatus(s) {
    if (s.status) return s.status.toLowerCase();
    var cpu = s.cpu, mem = s.mem;
    if ((cpu !== null && cpu >= 90) || (mem !== null && mem >= 90)) return 'critical';
    if ((cpu !== null && cpu >= 70) || (mem !== null && mem >= 70)) return 'warning';
    if (cpu !== null || mem !== null || disk !== null) return 'healthy';   // ← disk 未声明
    return 'unknown';
}
```

本文件第 5 行是 `'use strict';`，所以这不是「意外读到全局变量」，而是直接
**`ReferenceError: disk is not defined`**。

**触发条件比看上去窄**（实测确认，勿凭直觉）：

```js
if (cpu !== null || mem !== null || disk !== null) return 'healthy';
```

`||` 是**短路**的，所以 `disk` 只有在 `cpu` 与 `mem` **双双为 null** 时才会被求值。
也就是说必须同时满足三个条件才会炸：

1. `s.status` 为假值（否则第一行就 return 了）；
2. `cpu` 为 `null` **且** `mem` 为 `null`（任一有值就短路，永远走不到 `disk`）。

实测举证（修改前的代码）：

| 输入 | 结果 |
|---|---|
| `status=null, cpu=50, mem=50` | `healthy`（短路，不炸） |
| `status=null, cpu=null, mem=50` | `healthy`（短路，不炸） |
| `status=null, cpu=50, mem=null` | `healthy`（短路，不炸） |
| `status=null, cpu=null, mem=null` | **`ReferenceError: disk is not defined`** |

**影响链**（条件满足时）：`transformService`（在 `fetchServices` 的 `.then` 里）→
`.map(transformService)` 整体抛出 → 被 `.catch` 接住 → 走 `showError()`，整个 Smart
Inspection 页面变成错误条（"应用指标加载失败：disk is not defined"）。

**为什么一直没暴露**：需要后端同时返回空 `status` **和**空的 cpu/mem。实测 agentflow
`/app-indicators` 的三个服务 `status` 恒为 `"HEALTHY"`，第一行就提前返回，所以这条路径
从来没被执行过 —— changelog `v1.2.2-smart-inspection-api-integration.md` 里把
「status=null → 按 CPU/Mem/Disk 推导」标为 `待验证`，确实一直未验证。

**为什么现在修**：本次改造让这两列从死值变成真实的问题计数，而这条崩溃路径一旦触发，
两列连同整张表一起消失 —— 把一个数据条件放大成了页面级故障。

---

## 改动明细

### 1. `js/app.js:1446-1456` — 补上声明，并加注释说明为何不能「顺手改进」

```diff
 function deriveStatus(s) {
     if (s.status) return s.status.toLowerCase();
-    var cpu = s.cpu, mem = s.mem;
+    var cpu = s.cpu, mem = s.mem, disk = s.disk;
     if ((cpu !== null && cpu >= 90) || (mem !== null && mem >= 90)) return 'critical';
     if ((cpu !== null && cpu >= 70) || (mem !== null && mem >= 70)) return 'warning';
     if (cpu !== null || mem !== null || disk !== null) return 'healthy';
     return 'unknown';
 }
```

**保持原意（存在性检查），刻意不做「改进」**：`s.disk` 来自 `item.blockIO`，是形如
`"8.2 MB/s"` 的**格式化字符串**，把它改成数值阈值比较（`disk >= 90`）没有意义 ——
字符串与数字比较恒为 false，判定会悄悄变成「永远不 healthy」。所以只补声明，不动逻辑。

> 另一处注意：`cpu !== null` 对 `undefined` 也为真，因此当后端返回 `cpu/mem` 缺失（而非显式
> null）时会落到 `'healthy'`。这是改造前就有的语义，本次**不改** —— 修 ReferenceError 是
> 明确的目标，改判定语义会让这次修改的风险面失控。

## 影响范围

| 场景 | 预期 | 实际 | 状态 |
|------|------|------|------|
| `status` 有值（线上恒为 HEALTHY） | 与修改前一致 | 首行提前返回，未走到该行 | OK |
| `status=null`，cpu 或 mem 有值 | 与修改前一致（短路，本就不炸） | `healthy` | OK |
| `status=null`，**cpu 与 mem 双 null**，disk 有值 | 修前整页错误条 → 修后 `healthy` | `healthy` | OK |
| `status=null`，cpu/mem/disk 三项皆 null | `'unknown'` | `unknown` | OK |
| `status=null, cpu=95` | `'critical'`（阈值分支未受影响） | `critical` | OK |
| `npm run build` | 通过 | 通过 | OK |

**验证方式**：把修改前/修改后的 `deriveStatus` 源码分别抽成模块直接单测（它是不依赖 DOM 的
纯函数），覆盖上表四种输入组合 —— 修改前第三行抛 `ReferenceError: disk is not defined`，
修改后正常返回。上表「实际」列即为该次运行的真实输出。
