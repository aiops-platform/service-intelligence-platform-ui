# v2.2.18 — 拆掉 Service Ops 里指向 `/entity/app/` 的链接（点它会把 Vue 应用套进自己的 iframe）

**日期**: 2026-09-20

**问题/背景**: Service Ops 的「Top apps by incident pressure」表，**行尾那个 `›` 箭头点一下就出事** ——
页面在 iframe 里渲染出 Vue 应用自己，再点一次再套一层，最后是四层「自己套自己」。

---

## 根因

箭头是个普通 `<a>`，指向**部署站**的实体详情页：

```js
// 0t1fyt7wcotiz.js（Service Ops 的 chunk）
<a href={`/entity/app/${appKeySlug(e.appKey)}/`}
   onClick={e => e.stopPropagation()}
   title={`Open ${e.label} detail page`}>›</a>
```

它**不是** Next 的 `<Link>`，所以走整页导航。而那条路径在本仓里根本不存在 ——
离线副本的 `public/` 只有 `constellation-app.html` / `business-ops/` / `service-ops/`，
`sipEmbedPageIndex` 也只拦尾斜杠结尾的那两个：

```
/entity/app/xentry-work-order/  →  Vite SPA 兜底  →  Vue 应用的 index.html
                                 →  vue-router catch-all `/:pathMatch(.*)*`
                                 →  redirect /service-ops
                                 →  ServiceOpsView 又渲染一个 /service-ops/ 的 iframe
                                 →  ★ 在 Service Ops 里看到 Service Ops
```

实测（`curl` 对比，见「影响范围」）：

| 请求 | 返回 |
|---|---|
| `/service-ops/` | Next 内嵌页（命中 `sip-embed-shell-strip`） |
| `/entity/app/xentry-work-order/` | `<div id="app">` + `/src/main.js` —— **Vue 应用自己** |

生产 nginx 的 `try_files $uri $uri/ /index.html` 行为相同，所以这不是 dev 专有。

## 改动明细

### 1. `tools/tenant_copy.py` — 新增 `patch_service_ops_entity_links()` (~398)

**原因**: 两个锚点都要拆。处置**不同**，因为二者处境不同：

| 锚点 | 位置 | 处置 |
|---|---|---|
| ① 行尾 `›` | 表格行 | `preventDefault` + 调本行已有的 `onSelect`（`i`）→ 打开右侧 inspector |
| ② `→ Open detail · /entity/app/…` | inspector 页脚 | **整条去掉** |

```js
// ① before
(0,n.jsx)("a",{href:`/entity/app/${…}/`,onClick:e=>e.stopPropagation(),
  title:`Open ${e.label} detail page`,…,children:"›"})

// ① after —— `i` 就是整行 onClick 用的那个 onSelect，不新增状态
(0,n.jsx)("a",{href:"#",onClick:e=>{e.preventDefault(),e.stopPropagation(),i()},
  title:`Show ${e.label} details`,…,children:"›"})
```

② 那条在 inspector 里，**该 app 已经选中、面板已经开着** —— 既没有可跳的目标，也没有可再
选中的东西，所以整条去掉。留一个「点了没反应」的死链比没有更糟（正是 CLAUDE.md 反复点名的
「静默失败」）。

**没有换成 `/service-ops/?app=<key>` 深链**：那条会**重载 iframe**，把用户设的筛选
（journey / portfolio / tier / HC / bot）全部丢掉 —— 为了一个本来就不存在的目标页不值得。

### 2. `tools/make-offline-page.py` — 调用新补丁 (~352)

**原因**: 补丁必须由构建脚本调用，才会写进 `public/` 的产物。

### 3. `tools/tenant_copy.py` — 新增 `patch_default_tenant()` (~862)

**原因**: **顺手修掉一个「重建即回退」的坑，不是本次需求**。

重建产物时发现 `public/_next/static/chunks/0wuztp2.9oz~8.js` 与 HEAD 差了一处：

```diff
-if (t && t in tg) return t } catch {} return "otr" }()
+if (t && t in tg) return t } catch {} return "retail" }()
```

`cf01394`（「新增 otr 租户…并设为默认」）那一处是**手改在产物里的** —— 构建脚本每次都从
`tools/vendor/` 的原始外壳重铺 `public/_next/`，手改没有任何工具会写回去。后果是**任何一次
重建都会把默认租户悄悄变回 `retail`**，而构建输出一切正常、不报错。现在它是一个声明式补丁，
和本文件里其余十几处一样。

### 4. `src/components/NextEmbed.vue` — 新增自嵌闸门 `inSameOriginFrame()` (~61)

**原因**: 上面拆的是**今天已知的那两个链接**。宿主被套进自己的 iframe 是一类故障，
下一次换个链接（或者换个内嵌页）就会复发，所以补一道结构性的闸。

```js
const selfEmbedded = inSameOriginFrame()   // 同源祖先才算；跨源是正常的第三方嵌入
```

命中时**不渲染 iframe**，改显示一句说明。判据为什么是「同源」而不是「在不在 iframe 里」：
跨源 iframe 是正常的第三方嵌入（别人把 SIP 挂进自己页面），那时本组件应当照常工作；
跨源读 `window.top.location` 会抛，正好用来区分。

### 5. `css/styles.css` — `.cs-embed__guard*` (~7647)

**原因**: 上面那块替代内容的样式，与 `.cs-embed__mask` 同族（占满同一块地方）。
