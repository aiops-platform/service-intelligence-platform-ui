# v2.6.2 — Ticket Inbox 的 SEVERITY 列：同一列三种长相，加一层归一化映射

**日期**: 2026-09-22

**问题**: 「红圈部分展现形式不一致，P1、MEDIUM 分别代表什么」——Ticket Inbox 的
SEVERITY 列里，`HIGH` 是红底徽标，`P1` 和 `MEDIUM` 却是普通黑字。

---

## 症状（改前实测，值取自真实页面）

```
HIGH   | severity-high   | rgb(254, 242, 242)   ← 红底徽标   ×13
MEDIUM | severity-medium | rgba(0, 0, 0, 0)     ← 全透明背景 ×2
P1     | severity-P1     | rgba(0, 0, 0, 0)     ← 全透明背景 ×1
-      | (无 .alert-tag) | —                    ×12
```

## 根因：类名裸拼，而只有 4 条规则

模板里是 `:class="'severity-' + t.severity"`，而 `css/styles.css` 只定义了
`severity-critical` / `severity-warning` / `severity-info` / `severity-high` 四条。

**关键在于 `.alert-tag` 基类里既没有 `background` 也没有 `color`** ——
所以没命中的值不是"被设计成中性灰"，而是**一点样式都没有**，呈现为继承色的普通文本
（实测 `rgba(0,0,0,0)` + `rgb(17,24,39)`）。**"没样式"在页面上看起来像"忘了做"。**

## P1 / MEDIUM 分别是什么

两者都**不是平台的档位概念**，只是工单 `severity` 字段里的原始字符串
（后端该列是自由文本，建单时从 payload 原样存）：

- **`medium`** —— 前端**建单表单自己提供的选项之一**（critical/high/medium/low）。
  ⚠️ 所以这不是"历史脏数据"：**从表单正常选 medium 建出来的工单，本来就会显示成黑字**，
  当时仍在持续产生。
- **`P1`** —— ServiceNow 的 priority 写法，被原样带了进来。**代码里没有任何地方产出它**，
  它是"另一套词表"。

另有一个潜伏坑：Vue 这边**没有 lowercase**，而 legacy `js/app.js` 全都 `.toLowerCase()` 了。
所以一条大写的 `HIGH` 会让 `severity-HIGH` 匹配不上 `severity-high` —— 又是同一个静默退化。

---

## 改动

### 1. 新增 `src/utils/severity.js` —— 归一化映射层

仿 `utils/runStatus.js` 的既有范式（一张表 + 回退），导出
`severityTier` / `severityLabel` / `severityClass`。

- 词表：平台四档 + `p0`–`p4`（`p4`→`low` 而不是 `medium`：priority 数字越大越不紧急，
  一起塞进 medium 等于把"最低"说成"中等"）。表集中一处，以后接别的来源只改这张表。
- **先 `trim().toLowerCase()`** —— 一并堵掉上面那个大小写坑。
- 认不出来 → `'unknown'`，**不兜底到某一档**：让 `P9` 显示成 `MEDIUM` 是把
  "我们不知道"说成了一个具体的严重程度。**但 `unknown` 的文案保留原值**
  （`P9` 仍显示 `P9`）—— 工单是分诊工具，抹成 `UNKNOWN` 等于把线索删了。

### 2. `css/styles.css` —— 补 3 条规则（**只增不改**）

```css
.alert-tag.severity-medium   { background: #fffbeb; color: #d97706; }
.alert-tag.severity-low      { background: #ecfdf5; color: #059669; }
.alert-tag.severity-unknown  { background: #f3f4f6; color: #6b7280; }
```

现有 4 条一行未动。先例：`severity-high` 自己就是 v1.7.0 为 Problem Center 后加的。

**`severity-unknown` 是刻意多出的一条**，不是兜底：没有它，未命中的值仍会落到
`.alert-tag` 基类上 —— 那正是本次要消灭的隐式兜底。有了它，"未知"才是一个
**被明确选择过**的外观。（同文件 `status-escalated` 的注释早写过同一件事：
「**不写这条不会报错**，只是白底黑字像漏了样式」。）

### 3. `src/views/tickets/TicketsView.vue` —— 两个调用点改用映射层

表格 (`:210`) 与详情抽屉 (`:272`) 此前是同一段裸拼代码的两次复制，两处都换。
改后**类名与文案同源**（此前类名取原值、文案取大写，两者口径不同）。
文件头「不新增样式」那句也随之更正。

### 4. ⚠️ 一个被自己方案漏掉、实现时补上的回归

写 CSS 时发现：`.severity-warning` / `.severity-info` **是存在的**，而 `warning`/`info`
**不属于平台四档** —— 按最初的映射表，一条 `warning` 会从今天的**琥珀徽标**
掉成灰色的 `UNKNOWN`。那是我引入的新回归，不是修 bug。

故加了 `PASSTHROUGH`：`warning` / `info` 作为**认得但不折叠**的既有值原样透出。
判据是——折叠会**改变现有外观**，而把认得的东西说成 `unknown`，与把 `P1` 说成 `MEDIUM`
是同一种错误：都在撒谎。

## 验证（CDP 对真实页面；本仓无前端测试框架）

**改前 → 改后，逐条比对同一组 DOM 指标：**

| 值 | 条数 | 改前 | 改后 |
|---|---|---|---|
| `high` | 13 | `severity-high` 红 | **不变**（无回归） |
| `medium` | 2 | `severity-medium` **全透明** | `severity-medium` **琥珀** `rgb(255,251,235)` |
| `P1` | 1 | `severity-P1` **全透明** | **`CRITICAL`** + `severity-critical` 红 |
| 空 | 12 | `-` | **`-`**（不变） |

**真实模块的输入表**（`import()` 真身跑 21 个输入，不是重写一遍逻辑测自己）：
四档本体、大小写/空白（`HIGH` / `"  Medium  "`）、`P0`–`P4`、
`warning`/`info` **原样透出**、`P9`/`blocker`/`weird-thing` → `unknown` 且**保留原值**、
`null`/`undefined`/`''`/空白 → 三函数均返回 `''`。全部符合设计。

**未知档的真实渲染**：数据里没有未知值，造一条真工单会污染 `otr`（无删除端点），
故**只改浏览器**——拦截 `fetch` 给 `/tickets` 注入一行 `severity:"P9"`，走真实组件渲染：

```
cellText: "P9"                        ← 原值保留，没被抹成 UNKNOWN
tagClass: "alert-tag severity-unknown"
bg:       rgb(243, 244, 246)          ← 灰底生效（改前是 severity-P9 + 全透明）
```

**详情抽屉**（第二个调用点）：点 `INC-APPR-CHK` → `severityCRITICAL` +
`alert-tag severity-critical` + `rgb(254,242,242)`。

`npm run build` 通过。

### ⚠️ 未验证 / 有意不做

- **legacy 告警表的影响未能枚举**：`css/styles.css` 是双世界共享，`js/app.js` 的告警表
  也拼 `'severity-' + sev`（`:1993` / `:3701` / `:3900` / `:4308` / `:4386`，值已 lowercase）。
  所以那边**若存在** `medium`/`low` 的数据，会一并从黑字变成徽标。
  其数据源是 `http://localhost:8080/api/sip-aiops/app-alert`（真后端、非 mock），
  **本机该服务未运行，无法枚举实际取值** —— 记为未验证，不声称安全。
- **不动 `js/app.js` 的渲染逻辑**（只被动继承新 CSS）。
- **不动 `LogAnalysisView.vue:191`**：日志告警是另一套数据源、取值空间
  （info/warning/critical）与工单不同，且它自己做 lowercase。留作后续。
- **不在后端归一化、不迁移存量数据**：`severity` 存的是"源系统当时说的是什么"，
  是有据可查的记录；归一化是**展现层**的事。写回规范值既丢信息，又要碰已有数据。
