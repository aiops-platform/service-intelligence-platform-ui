# v2.3.2 — View diagnosis 概要条加 Flow Diagram 入口：一键只看「最后一次执行」的流程图

**日期**: 2026-09-21

**需求/背景**: 「能不能在 view diagnosis 按钮打开的第一个页面的最上边和状态来源那一行后边，
放一个 Flow Diagram 按钮，展示最后一个历次执行 · EXECUTIONS 的最后一次的 Flow Diagram」。

改之前要看某轮的执行流程，得滚到弹框最底部的「历次执行 · EXECUTIONS」再点那一行 ——
而多数时候想看的就是**当前这一轮**，等于每次都要滚到底。

两条追加要求（同一轮迭代内）：

1. 「这个颜色能不能和历次执行 · EXECUTIONS 中的按钮颜色一样」
2. 「我点击的时候只展示一个图，不要展示历史执行的窗口」

## 改动明细

### 1. `js/app.js:5117` — `dgxLastExecution()` / `dgxLastRunId()`

```js
function dgxLastExecution(snap) {   // is_current 优先，回落数组末条
    var items = (snap && snap.executions) || [];
    if (!items.length) return null;
    for (var i = 0; i < items.length; i++) if (items[i] && items[i].is_current) return items[i];
    return items[items.length - 1];
}
```

**不能用「列表里最后一个」当最后一次**：`dgxExecutions` 渲染时把「进行中」置顶
（为的是让用户先看到"现在跑到哪了"），于是**最后一次正在跑时它反而排在第一条**，
渲染顺序与数组顺序不同。真源是后端契约 —— `fetch_executions` 按 evidence 写入顺序返回、
**最后一条**打 `is_current`（重跑追加在尾部）。实测 6 轮的单：
`run_070989275c … run_ba913bc09c(is_current)`，时间戳递增，末条即最新。

### 2. `js/app.js:5137` — `dgxFlowBtn()`：显隐与点击**共用** `dgxLastRunId`

`if (!dgxLastRunId(snap)) return '';` —— 没有可开的 run（老 spike 记录没有 agentflow run、
或这条单还没 Analyze 过）时**不渲染按钮**，而不是渲染一个点了没反应的死按钮。
判据只写一份，按钮的显隐与点击处理器都走它，不会漂移。

按钮不带 `data-exec-run`：轮次在点击时现算，免得"哪条是最后一次"在标记与处理器里各写一份。

### 3. `js/app.js:5243` — 插进吸顶头部的状态行右端（`dgx-head-right` 右对齐簇）

```js
'<span class="dgx-head-right">' +
  dgxFlowBtn(snap) +
  (snap.updated_at ? '<span class="dgx-updated">更新 …</span>' : '') +
'</span>'
```

簇内顺序是**按钮在左、时间贴最右**（先写成"时间在前"、按用户反馈换过位置）。
`margin-left:auto` 从 `.dgx-updated` **上移到外层簇**：两个 auto 会平分空白，
把「更新」挤到行中间去。（`.dgx-updated` 全仓只有这一处使用，挪动无副作用。）

### 4. `js/app.js:6253` + `openProblemRun(rec, runId, opts)` — 点击**只开一张图**（`opts.silent`）

```js
openProblemRun(pcDiagRec, lastRid, { silent: true });
openRunGraph();
```

`opts.silent` = 只备数据、**不亮 run 查看器**。图弹框与 run 查看器共用本轮全部管道
（`pcRunId` / 2s 轮询 / `pcRunGraph`），差别只有"主弹框亮不亮"这一件事，所以是同一个函数加一个开关，
而不是复制一份。**顺序不能反**：`openProblemRun` 开头会 `closeRunGraph()` 清残留，
且它负责建 `pcRunId` 与数据管道，`openRunGraph` 才有东西可画（数据未到时先显示
`Loading flow diagram…`，`applyRunView` 拿到 run 后补画，既有机制）。

落点是**既有**的二级弹框 `#pcRunGraphOverlay`（与「历次执行」行、与 Bug Solve 共用同一个查看器）。

**配套：`closeRunGraph()` 补静默收摊**（`js/app.js:6096`）。停轮询原本只挂在
"关 run 查看器"（`closeProblemRun`）上，而静默模式**根本没开过**那个弹框 ——
不补这一步，关掉图之后那个 2s 轮询会一直在后台跑。收摊放在 `closeRunGraph` 里
（读了 `pcRunSilent` 就先清标志再 `closeProblemRun()`，避免自递归）。

### 5. `css/styles.css:6813` — `.dgx-head-right` + `.dgx-btn.dgx-flowbtn`

- **尺寸**对齐旁边的 chip（`padding: 2px 10px; font-size: 11px`）：按钮比 chip 高的话
  吸顶条会跟着变厚，滚动时白占一截可视区。
- **配色**对齐「历次执行」行尾的 `查看执行流程 ›`（`.dgx-exec-go` 的 `--accent-blue`）+
  `.dgx-exec-row` 的蓝色 hover 描边。同一个动作的两个入口（概要条按钮 / 行尾链接）长一样，
  而不是一个黑粗体一个蓝。

## 踩坑记录

**坑 1：`.dgx-flowbtn` 的样式没生效。** 第一次写成单类 `.dgx-flowbtn`，实测按钮仍是 29px 高
（`.dgx-btn` 的原尺寸），把状态行从 21px 撑到 29px。原因不是权重算错，是**源码顺序**：
`.dgx-flowbtn` 写在 6819 行、`.dgx-btn` 在 7183 行，两者都是单类（权重相同 0,1,0）→
**后写的赢**，整条规则被 `.dgx-btn` 盖掉。改成复合选择器 `.dgx-btn.dgx-flowbtn`（0,2,0）才稳定胜出。
（已把这条陷阱记进 `CLAUDE.md` 的「样式」节。）

**坑 2：静默收摊把**新**会话拆了 —— `pcRunSilent` 的读写顺序。**
`openProblemRun` 内部本来就有一句 `closeRunGraph()`（清上一轮残留的图弹框），
而我把 `pcRunSilent = <本轮值>` 放在了它**前面**。于是收摊逻辑读到的是"本轮"的静默标志，
把刚建好的会话当成上一轮给拆了：

```
pcRunSilent = true          ← 本轮设的
closeRunGraph()             → 读到 true → 清标志 + closeProblemRun()
                              → pcRunId = null / pcRunData = null
if (!pcRunSilent)           → 此时已是 false → run 查看器照开（症状 1）
fetchRunNow()               → pcRunId 为 null，直接空转 → 图永远停在 Loading（症状 2）
```

**症状 1 与症状 2 是同一个根因**，只是看的地方不同；当时只盯"静默没生效"会漏掉第二处。
修法：把那句 `closeRunGraph()` 提到所有状态赋值**之前** —— 收摊永远该按**上一轮**的标志做。
